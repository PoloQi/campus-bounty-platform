# 管理端接口验证手册

> 目的：不依赖管理前端，也能亲手验证管理端 20 个接口是否真的可用。
> 适用范围：`campus-bounty-user-backend` 的 `/api/admin/**`。
> 一键脚本：`scripts/admin-smoke/smoke.py`
> 最近更新：2026-11-18

---

## 零、先分清两条验证路径

这是最容易搞混的一点：**「验证功能对不对」和「验证线上配置对不对」是两个不同的问题，需要不同的数据库。**

| 路径 | 数据库 | 能验证什么 | 会写数据吗 | 用哪个模式 |
|---|---|---|---|---|
| **A. H2 内存库** | `test` profile，Hibernate 自动建表，进程退出即消失 | 完整业务链路：注册 → 充值 → 发单 → 接单 → 举报处置 → 封禁解封 → 申诉仲裁 | 会，但只写在内存里，杀进程就没了 | `--mode full` |
| **B. 共享 MySQL** | `local` profile，团队共用真库 | 服务能否启动、`ddl-auto=validate` 是否通过、真实库上的接口返回结构 | **不要写** | `--mode readonly` |

> 为什么不建议对真库跑 `full`：它会注册 5 个用户、发一笔悬赏、封禁并解封一个人、提交并处置一条举报、走完一次仲裁（**会真的改钱**），这些都会留在团队的共享库里。而且真库 `max_user_connections` 只有 10，起服务本身就快占满了。

> MySQL 启动需要当前的 `t_admin_log` 及 `t_report` 上的 `handler_id`、`handled_at`、`result`、`handle_comment`。新库执行 `schema.sql`，现有库先备份并执行迁移。旧版 `admin_log` 和 `t_report_resolution` 在存在时用于回填。参见[数据库升级步骤](../frontend/README.md#后端配置与数据库升级)。

## 三、不用脚本，手工验证（答辩演示用）

以下命令按顺序执行，变量会逐步建立。用 Git Bash。

### 3.1 拿 admin token

```bash
BASE=http://localhost:8080
read -r -p "管理员账号: " ADMIN_USERNAME
read -r -s -p "管理员密码: " ADMIN_PASSWORD
printf '\n'
TOKEN=$(printf '%s\n%s\n' "$ADMIN_USERNAME" "$ADMIN_PASSWORD" | \
  python -c "import sys,json; print(json.dumps(dict(zip(('username','password'),sys.stdin.read().splitlines()))))" | \
  curl -s -X POST "$BASE/api/auth/login" \
  -H "Content-Type: application/json" \
  --data-binary @- | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")
unset ADMIN_PASSWORD
```

在 `local` 或 `test` profile 中，未配置初始化凭据时可使用演示账号 `admin` / `admin123`。其他环境使用部署时设置的管理员凭据。

### 3.2 数据看板（一屏看全）

```bash
curl -s $BASE/api/admin/dashboard -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

关注四点：

1. `data.totals` 六个字段齐全：`students / orders / gmv / frozen / openAppeals / pendingReports`
2. `data.distribution` **固定 6 项**，缺的状态补 0——不是只返回有数据的几个状态
3. `data.trend` **固定 7 项**，日期连续升序，最后一项是今天
4. `sum(distribution[].total) == totals.orders`

第 4 点是最容易出问题的地方：如果两个数字来自两条独立的 SQL 而不是同一时刻，中途有人下单就会出现「总数 21、分布加起来 20」。

**答辩话术**：分布用 `List` 而不是 `Map`，是因为 `Map` 的 JSON 序列化顺序不可依赖，饼图图例会随机跳。趋势先铺 7 天 0 再覆盖真实值，否则前端折线图会把 3 个点均匀铺满横轴，看起来像天天都有单——这种静默错误比少个字段危险。

### 3.3 订单列表（分页 + 筛选）

```bash
curl -s "$BASE/api/admin/orders?status=COMPLETED&page=0" -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

- 返回结构是 `{items, page, hasNext}`，不是裸数组
- 可用参数：`status`（枚举名，如 `IN_PROGRESS`）、`type`（`BOUNTY`/`SERVICE`）、`buyerId`、`sellerId`、`from`、`through`（`yyyy-MM-dd`）、`page`
- 只读：这个接口没有任何写方法，管理端看得到但改不了订单

### 3.4 订单详情（一屏取证）

```bash
curl -s "$BASE/api/admin/orders/1" -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

返回 7 个聚合块：`order`、`post`、`buyer`、`seller`、`logs`（资金流水）、`appeals`（申诉）、`timeline`（时间线）。

**答辩话术**：详情里 `buyer`/`seller` 是白名单 DTO（只含 id/username/nickname/role/status/createdAt），**没有 `passwordHash`**。用户摘要一律不透传实体，避免密码哈希随一个「查看详情」接口泄漏。

### 3.5 验证「管理端改不了钱」

这是设计上的硬约束，值得当面演示：

```bash
# 试遍所有可能的调账写法，全部 404 或 405
curl -s -X POST "$BASE/api/admin/users/1/wallet/adjust" -H "Authorization: Bearer $TOKEN" -d '{"amount":1000}'
```

管理端**没有**任何调账、改余额、补录流水的接口。钱的去向只能由订单状态机驱动（托管 → 结算/退回），管理员能做的是「裁决」，不是「直接改数字」。这一条在答辩上比多写十个接口更有说服力。

### 3.6 用户与资金

```bash
curl -s --get "$BASE/api/admin/users" --data-urlencode "keyword=$ADMIN_USERNAME" -H "Authorization: Bearer $TOKEN" | python -m json.tool
curl -s "$BASE/api/admin/users?status=BANNED" -H "Authorization: Bearer $TOKEN" | python -m json.tool
curl -s "$BASE/api/admin/funds" -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

`/funds` 返回三个数：

- `frozen`：`SUM(wallet.frozen)`，平台上真实躺着的托管款
- `expected`：`SUM(trade_order.amount) WHERE status IN (PENDING, IN_PROGRESS, CONFIRMING, DISPUTED)`，在途订单「应该」冻结的金额
- `difference`：`frozen - expected`，正常恒为 0

**答辩话术**：`difference != 0` 就是账不平。这个数不需要人工算，每次看一眼就知道钱有没有凭空多出来或少掉。

### 3.7 资金账本与审计

```bash
curl -s "$BASE/api/admin/funds/ledger?userId=1" -H "Authorization: Bearer $TOKEN" | python -m json.tool
curl -s "$BASE/api/admin/audit?action=BAN_USER" -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

账本可按 `userId / type / orderId / from / through` 过滤；审计可按 `adminId / action / from / through` 过滤。两者都返回分页结构。

审计动作名：`DELETE_POST`、`CLOSE_TRADE_POST`、`BAN_USER`、`UNBAN_USER`、`HANDLE_REPORT`、`ARBITRATE_APPEAL`。

**答辩话术**：每个管理动作都在同一事务里写一条审计。审计失败则动作回滚——留痕不是「尽力而为」，是前置条件。

### 3.8 举报处置闭环

先造一条举报（用学生 token）：

```bash
STU=$(curl -s -X POST $BASE/api/auth/register -H "Content-Type: application/json" \
  -d '{"username":"demo_stu","password":"123456","confirmPassword":"123456","nickname":"演示学生"}' >/dev/null; \
  curl -s -X POST $BASE/api/auth/login -H "Content-Type: application/json" \
  -d '{"username":"demo_stu","password":"123456"}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

curl -s -X POST $BASE/api/reports -H "Content-Type: application/json" \
  -H "Authorization: Bearer $STU" \
  -d '{"targetType":"TRADE_POST","targetId":1,"reason":"演示：疑似刷单"}'
```

管理员看和处理：

```bash
# 待处理列表（只返回 PENDING）
curl -s $BASE/api/admin/reports -H "Authorization: Bearer $TOKEN" | python -m json.tool
# 分页查询（可按 status/targetType 过滤）
curl -s "$BASE/api/admin/reports/query?status=PENDING" -H "Authorization: Bearer $TOKEN" | python -m json.tool
# 处置前预览对象现状
curl -s "$BASE/api/admin/moderation/TRADE_POST/1" -H "Authorization: Bearer $TOKEN" | python -m json.tool
# 判定成立并顺带下架
curl -s -X POST "$BASE/api/admin/reports/1/handle" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"result":"VALID","moderate":true,"comment":"核实成立，下架处理"}'
# 回看处置结果
curl -s "$BASE/api/admin/reports/1" -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

预期：`status=HANDLED`、`result=VALID`、`moderationAction=CLOSE_TRADE_POST`、`adminId`/`handledAt` 有值，对应交易帖变为 `CLOSED`。

两个必须验证的拒绝路径：

```bash
# 驳回却要治理 → 40000（不允许无依据处罚）
curl -s -X POST "$BASE/api/admin/reports/2/handle" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" -d '{"result":"REJECTED","moderate":true,"comment":"驳回但要下架"}'
# 已处理的举报再处置 → 40000
curl -s -X POST "$BASE/api/admin/reports/1/handle" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" -d '{"result":"REJECTED","comment":"再处理一次"}'
```

**答辩话术**：处置建模成「先判成立（`result`），再决定是否治理（`moderate`）」，而不是「一个 action 包办两件事」。因为「判定」和「处罚」是两件独立的事：可以让举报成立但只警告不处罚，也可以驳回。把两件事压成一个字段，等于把业务规则硬编码进枚举。

### 3.9 封禁与解封

```bash
# 封禁（只能封 STUDENT，封管理员会被拒）
curl -s -X POST "$BASE/api/admin/users/2/ban" -H "Authorization: Bearer $TOKEN"
# 该用户旧 token 立刻 401
curl -s -o /dev/null -w "%{http_code}\n" $BASE/api/trade/posts -H "Authorization: Bearer $STU"
# 解封
curl -s -X POST "$BASE/api/admin/users/2/unban" -H "Authorization: Bearer $TOKEN"
# 同一枚 token 立刻恢复 200
curl -s -o /dev/null -w "%{http_code}\n" $BASE/api/trade/posts -H "Authorization: Bearer $STU"
```

**一个必须知道的语义**：解封后**旧 token 自动恢复可用**。`JwtAuthFilter` 每请求查库，`BANNED` 只是「当次不往 SecurityContext 写认证」，token 本身从未被吊销，系统也没有黑名单机制。所以封禁期间 401、解封后立刻 200。

若将来引入 token 吊销（黑名单/版本号），必须同步修改三处：`AdminActionAcceptanceTest.ban_then_unban_restores_login_capability`、冒烟 `[14]`、本节。

### 3.10 申诉仲裁（唯一会动钱的管理端接口）

```bash
# 学生发起申诉（订单须在 IN_PROGRESS / CONFIRMING）
curl -s -X POST "$BASE/api/trade/orders/1/appeal" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $STU" -d '{"reason":"已完成跑腿，对方拒付"}'

# 待裁决列表
curl -s "$BASE/api/admin/appeals?status=OPEN" -H "Authorization: Bearer $TOKEN" | python -m json.tool

# 判付给卖家
curl -s -X POST "$BASE/api/admin/appeals/1/arbitrate" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"outcome":"RELEASE_TO_SELLER","comment":"核实已完成交付，判付"}'

# 退款给买家
curl -s -X POST "$BASE/api/admin/appeals/2/arbitrate" -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"outcome":"REFUND_TO_BUYER","comment":"服务未交付，全额退款"}'
```

预期（判付）：卖家 `balance +amount`、买家 `frozen -amount`、订单 `COMPLETED`、**悬赏帖 `CLOSED`**、申诉 `RESOLVED`、审计 1 条 `ARBITRATE_APPEAL`、买卖双方各 1 条 `APPEAL_RESOLVED` 通知、`/funds` 的 `difference` 不变。

预期（退款）：买家 `frozen` 归零、`balance` 回到原值、订单 `CANCELLED`、**服务帖保持 `OPEN`**（一帖多单，一笔纠纷不该影响其他人继续下单）。

三条必须验证的拒绝路径：

```bash
# 处理意见为空 → 40000（仲裁必须说明理由）
# 重复裁决 → 40000，且余额不再变化（钱只动一次）
# 已撤回的申诉再裁决 → 40000
```

**答辩话术（为什么先锁再判）**：`arbitrate` 先用 `findByIdForUpdate` 锁订单行、再锁申诉行，最后才校验状态。顺序反过来时，两个管理员同时点裁决，会各自通过校验、各打一次钱；现在的写法让后到的那个阻塞在锁上，等前者提交后读到 `RESOLVED`，在动钱之前就被 `40000` 拦下。

**第二个话术（钱为什么不手写）**：资金只走 `WalletService.settle/unfreeze`，不手写余额加减。那两个方法内部有「冻结额够不够」的校验并写 PAY/INCOME 流水，绕开就等于绕开冻结校验——账面上看着对，实际已经透支。

### 3.11 完整链路一次跑完

不想逐个点，直接：

```bash
python scripts/admin-smoke/smoke.py --mode full  # 先设置隔离测试环境的管理员凭据
```

它会把这 20 个接口按业务顺序串起来，58 项断言全过才返回 0。

## 四、常见失败与对应原因

| 现象 | 原因 | 处理 |
|---|---|---|
| 401 | 没带 token，或用户被封禁 | 检查 `Authorization: Bearer`；封禁期 401 是预期行为 |
| 403 | 用的是学生 token | 用已配置的管理员账号登录。管理接口要求 `role=ADMIN`。 |
| `Schema-validation: missing table [t_admin_log]` 或 `[t_report]` 缺字段 | 当前库未完成管理表迁移 | 核对连接目标，按[数据库升级步骤](../frontend/README.md#后端配置与数据库升级)备份并迁移。 |
| `Too many connections` | 共享库 `max_user_connections=10`，忘了停服务 | 停掉多余进程；建议 local 配 `hikari.maximum-pool-size: 3` |
| 业务码 `40000` | 业务校验未通过 | 看 `message`：多为「已处理」「不允许此操作」「订单当前不在纠纷中」 |
| 注册返回 `40000` | 用户名长度不在 4–20 | 用 `smb123456` 这类短名 |
| 发帖返回 `40000` | `deadline` 为空或早于当前时间 | 悬赏发布必须带未来截止时间；服务发布不需要 |
| 冒烟报「无法连接」 | 服务没起或端口不对 | 先确认 `Started BountyApplication`，再用 `--base` 指定地址 |
| 冒烟「冻结为 0」失败但打印 `frozen=0.0` | Python 里 `float(x or -1)` 把 `0.0` 当假值 | 脚本已改用 `num_of()`，不要回退成 `or -1` 写法 |
| `不支持发行版本 17` | `JAVA_HOME` 指向 JDK 11 | `export JAVA_HOME="/c/Program Files/Java/jdk-17.0.19"` |

## 五、脚本退出码

| 退出码 | 含义 |
|---|---|
| 0 | 全部通过 |
| 1 | 有失败项，末尾会列出未通过项名称 |

`--mode full` 未提供已有学生凭据时会创建临时学生账号来检查权限。
