### 关键设计取舍

1. **postType 筛选要跨表，用 HQL 实体 join**：`TradeOrder` 没有映射 `@ManyToOne TradePost`（既有代码一直是裸外键 id），所以写 `left join TradePost p on p.id = o.postId`。用 left join 而不是逗号连接，是为了「帖子缺失时订单行不消失」——脏数据下仍能看到订单，只是 `p.type` 为 null。
2. **不加后端分页**：设计 §6 明确「全量列表 + 前端 Element Plus 分页」。加 `Pageable` 会与本仓库零使用的范式冲突，也会让前端多处理一层 envelope。
3. **用户摘要用白名单构造，不返回 `User` 实体**：`UserBrief.of(user)` 逐字段赋值，天然不含 `passwordHash`。若改用 `@JsonIgnore` 黑名单，实体新增敏感字段时会默认泄漏。测试直接断言响应原文不含 `passwordHash`/`password_hash` 与真实哈希值。
4. **详情用 `@Transactional(readOnly = true)`**：跨 5 张表的多次查询落在同一快照，避免读到「订单已结算、流水还没刷出」的中间态。
5. **`seller` 允许为 null**：悬赏 `PENDING` 时 `seller_id` 本就为空，强行报错会让列表里最常见的状态打不开详情。
6. **不存在的订单返回 `40000` 而非 500**：沿用 `BizException` 默认码，前端按 code 提示即可。

### 关键设计取舍

1. **不提供任何写入口**：后台充值、扣减、调账一律不做，管理员影响资金的唯一合法路径是申诉仲裁。这不只是省事，是防止「有权限就能改钱」这类最危险的越权。
2. **`userWallet` 的钱包缺失时返回零值视图，不落库**：`walletService.getOrCreate` 会写库，管理端只读查询不能顺手造数据。用户不存在则报 `40000`（它是资源标识）；钱包缺失（脏数据）返回 `balance=0/frozen=0` 的空对象。
3. **`frozenSummary` 只呈现事实，不校验**：接口返回 `diff` 与 `balanced`，但不因差额非 0 而报错。因为测试环境本身就不守恒（见下方「验收方式调整」），报错会让接口挂掉；真实差额该由人看数字判断。
4. **`totalFrozen` 用 `coalesce(sum(...), 0)`**：`SUM` 在空表返回 null，兜住之后调用方不必判空。
5. **`inFlightOrderCount` 一并返回**：金额对不上时，能立刻看出是「一笔大额」还是「多笔小额」，省一次翻列表。
6. **`frozenSummary` 加 `@Transactional(readOnly = true)`**：两个 SUM 必须同一快照，否则中途有人冻结就会算出假差额。

### 验收方式调整（重要发现）

本板块原本打算断言「全局差额 diff == 0」。实际勘察发现**做不到**：
`WalletDomainTest` 里有多处 `walletService.freeze(user, AMOUNT, 101L)` 这类**用合成订单号直接冻结**的用例，库里根本没有 101–107 号订单。这些冻结会永久留在 H2 里（`DB_CLOSE_DELAY=-1`），导致「平台冻结总额」恒大于「在途订单金额」。

因此守恒断言改为**增量守恒**：执行一条资金路径前后，`diff` 的变化量必须为 0。测试覆盖全部四条路径：

| 路径 | 动作 | 期望 |
|---|---|---|
| 1 发布冻结 | 充值 100 → 发 20 元悬赏（PENDING） | diff 不变（冻结 +20，在途 +20） |
| 2 接单 | accept（PENDING → IN_PROGRESS） | diff 不变（只改状态不动钱） |
| 3 正常结算 | deliver → confirm（→ COMPLETED） | diff 不变（冻结 -20，在途 -20） |
| 4 取消解冻 | 发 15 元单 → cancel（→ CANCELLED） | diff 不变（冻结 +15 再 -15，在途同理） |

顺带说明：真实数据下这个指标应恒为 0。冒烟在**全新 H2 实例**上跑时就是 0（`frozen=20.0 inFlight=20.0 diff=0.0`），第二轮累积到两笔订单后依然守恒（`frozen=40.0 inFlight=40.0 count=2`）——这正好演示了指标成立的前提。

### 关于是否改用 `ddl-auto: update`

结论：**不改**。理由：

1. `application.yml` 是入库的团队共享配置，`validate` 是团队既定决策（防止程序误改结构），改它等于替全团队做决定。
2. `update` 会扫描全部实体的全部字段去对齐整库，在共享库上存在悄悄 ALTER 他人表的风险；且只加不减，长期会与 `schema.sql` 这份单一真源漂移。
3. 「不想装客户端 / 不想手动执行」这个诉求，用 JDBC 直连就能满足，无需动配置。

若确实想本地自动建表，可在**被 gitignore 忽略**的 `application-local.yml` 里加 `jpa.hibernate.ddl-auto: update`，只影响自己、不进仓库，但不建议长期开启。

## 六、环境注意（踩过的坑）

1. **`JAVA_HOME` 指向 JDK 11**（`D:\develop\Java\jdk-11`），而项目要求 17。直接跑 `./mvnw` 会报「不支持发行版本 17」。命令前需覆盖：
   ```bash
   export JAVA_HOME="/c/Program Files/Java/jdk-17.0.19"
   ```
2. **`./mvnw spring-boot:run -Dspring-boot.run.useTestClasspath=true` 不生效**（`application-test.yml` 未进 classpath，导致 `JWT_SECRET` 占位符解析失败）。改用显式 classpath 启动：
   ```bash
   ./mvnw -q dependency:build-classpath -Dmdep.outputFile=target/cp.txt -Dmdep.includeScope=test
   "$JAVA_HOME/bin/java" -cp "target/classes;target/test-classes;$(cat target/cp.txt)" \
       com.campus.bounty.BountyApplication --spring.profiles.active=test
   ```
   该方式用 H2 内存库自动建表，无需 MySQL 即可完成真实 HTTP 冒烟。
3. **测试用户名必须全局唯一**：H2 是 `DB_CLOSE_DELAY=-1` 且 Spring Context 缓存，同一 JVM 内数据跨测试类保留，重名会撞 `uk_user_username`。本板块用 `audit_` 前缀。
4. **跨测试类的历史数据会污染断言**：纯记录类断言用合成 `adminId`（`900001/900002/900003`）隔离；真实动作类断言用 `anyMatch` 找特定 `targetId`。
5. **共享库连接数上限只有 10**：报错 `User 'campus_user' has exceeded the 'max_user_connections' resource (current value: 10)`。本地用 `local` profile 起应用后，Hikari 默认池会把连接占满，此时任何其它客户端/JDBC 都连不上。**要查库就先停应用**，或在 `application-local.yml` 里调小 `spring.datasource.hikari.maximum-pool-size`（如 3）。
6. **jshell 输出含中文会被管道吞掉**：`grep` 会把含 CJK 的输出判成 binary 从而只打印 `Binary file (standard input) matches`。诊断脚本里输出一律用 ASCII（如 `RESULT key=value`）并 `grep -a`。
7. **注册用户名必须是 4–20 位**（`RegisterReq.username` 的 `@Size`）。冒烟脚本里用 `smoke_b2_pub_<时间戳>` 会超长，`/api/auth/register` 返回 `code=40000` 且后续 `login` 拿不到 token，报错位置会误导到登录。测试/冒烟用户一律用 `b2p<数字>` 这类短名。
8. **admin 演示账号密码是 `admin123`**，不是学生默认的 `123456`（`AdminBootstrap` 在 `local`/`test` profile 初始化）。
9. **`WalletDomainTest` 用合成订单号直接冻结**（`walletService.freeze(user, amount, 101L)` 等），库里没有这些订单。后果：H2 里「平台冻结总额」恒大于「在途订单金额」，**任何全局 `diff == 0` 的断言都会失败**。涉及冻结核对的测试必须用增量守恒（操作前后 diff 变化量为 0）。
10. **mvnw / curl 输出直接进管道时可能被安全策略截断**（表现为 `SENSITIVE_APPROVAL=TIMED_OUT`）。规避：输出重定向到 `target/xxx.log` 再用 Read 读，且日志里不要打印 token、密码、密码哈希原文。

## 七、下一个板块（B4 举报处置闭环）的开工清单

设计依据：`docs/superpowers/specs/2026-10-11-管理保障模块-设计.md` §5。`t_report` 的 4 个新列**已在真库与 `schema.sql` 落地**（见 §五），本板块只加实体字段，不需要再执行 DDL。

1. `Report` 实体补 4 个字段：`handlerId`、`handledAt`、`result`（VALID/REJECTED）、`handleComment`（≤500）。列已存在，加字段后 `local` 可直接启动。
2. `ReportRepository` 增 `searchForAdmin(status, targetType)`，两条件可选，按 id 倒序。
3. `AdminReportService`（新类）实现 `handle(...)`：
   - 校验举报存在且 `status=PENDING`（已处理的再处理要报错）
   - 校验 `action` 与 `targetType` 匹配：`POST` → `DELETE_POST`/`BAN_USER`/`REJECT`；`TRADE_POST` → `CLOSE_TRADE_POST`/`BAN_USER`/`REJECT`；`USER` → `BAN_USER`/`REJECT`
   - 执行处置后回写 `status=HANDLED`、`result`、`handlerId`、`handleComment`、`handledAt`
   - 写一条 `AuditAction.HANDLE_REPORT` 审计（**只写这一条**，不要复用 `AdminService.deletePost`，否则会多出一条 `DELETE_POST` 审计）
   - `NotificationService.push(reporterId, "REPORT_HANDLED", ...)`，文案区分「成立并已处置」与「驳回」

7. 新建 `AdminReportFlowTest`：四动作各一遍（断言被处置对象状态真的变了）、举报人收到通知、审计只有一条 `HANDLE_REPORT`、重复处理被拒、已 REJECT 的举报 result 为 REJECTED、学生 403。
