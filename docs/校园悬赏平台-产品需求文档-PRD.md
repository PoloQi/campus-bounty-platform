本文面向用户端开发成员、管理员端开发成员及共同验收人员。第二章是两端共同遵守的唯一业务规则来源；第三、四章分别作为两端的开发规格；第五章用于划分责任和组织联调。

## 一、文档说明与产品范围

### 1.1 产品定位

校园悬赏平台是面向高校学生的 C2C 互助悬赏交易平台。学生可以发布需求悬赏、挂牌技能服务、接单或下单，并通过“模拟余额 + 冻结托管 + 担保结算”完成交易；平台同时提供社区交流、一对一私信，以及纠纷仲裁、举报处理、资金监管和操作审计能力。

### 1.2 产品目标

1. **交易可信**：出资方发起交易时冻结资金，完成、取消或仲裁时按明确规则结算或退回。
2. **双模式统一**：需求悬赏与服务挂牌共用订单、状态机和资金规则，降低双端理解成本。
3. **交流可达**：支持图文社区、找搭子、私信、搜索和站内通知。
4. **平台可保障**：纠纷可申诉、申诉有裁决、举报有反馈、资金可核对、管理动作可审计。

### 1.3 角色与端边界

| 角色 | 使用端 | 核心能力 | 权限边界 |
|---|---|---|---|
| 未登录访客 | 用户端 | 注册、登录 | 交易、钱包、社区互动、私信、申诉、举报均需登录 |
| 学生用户（STUDENT） | 用户端 | 发悬赏、挂服务、接单、下单、发帖、私信、申诉、举报 | 不能访问 `/admin` 和 `/api/admin/**` |
| 平台管理员（ADMIN） | 管理员端 | 内容治理、用户治理、仲裁、订单与资金监管、看板、审计 | 不提供后台调账；订单资金归属只能通过申诉仲裁改变 |

“发布者、接单者、挂牌者、下单者、buyer、seller”是具体订单中的身份，不是独立账号角色。同一学生账号可以在不同订单中担任买方或卖方。

### 1.4 当前版本交付范围

| Sprint | 用户端交付 | 管理员端/平台交付 |
|---|---|---|
| Sprint 1 | 注册登录、注册开钱包、充值/余额/流水、悬赏发布与大厅、接单、交付、确认、取消、个人中心 | 钱包与订单领域规则；订单枚举预留 `DISPUTED`，暂不开放纠纷操作 |
| Sprint 2 | 资料编辑、服务挂牌与下单、社区、找搭子、私信、搜索、通知、互评 | 删帖、下架、封禁、举报列表等基础治理能力；Docker 部署 |
| Sprint 3 | 订单申诉/撤回、纠纷状态提示、内容举报、处理结果通知 | 独立 `/admin`：仪表盘、订单、申诉、举报、用户、资金、审计日志 7 个主页面 |

当前版本包含 Backlog 中的 P0、P1 条目。P2 条目统一放入 R3，不作为三个 Sprint 的验收前提。

### 1.5 本期非目标

- 不接入真实支付渠道，充值仅为模拟能力。
- 不提供管理员直接修改余额、冻结金额或补录资金流水的入口。
- 不提供群聊、私信已读回执。
- 不在当前版本实现帖子转悬赏、超时自动确认和信用分。
- 不把管理员端订单监管设计为另一套订单状态机。

## 二、共享业务契约

### 2.1 统一交易模型

| 规则 | 需求悬赏 BOUNTY | 服务挂牌 SERVICE |
|---|---|---|
| 帖主身份 | 需求方 | 服务提供方 |
| 他人动作 | 接单 | 下单购买 |
| buyer（出资方） | 帖主 | 下单者 |
| seller（收款方） | 接单者 | 帖主 |
| 发布时动作 | 创建 `PENDING` 订单并冻结赏金 | 只创建开放服务帖，不建单、不冻结 |
| 成交时动作 | 接单后进入 `IN_PROGRESS` | 下单即创建 `IN_PROGRESS` 订单并冻结货款 |
| 一帖订单数 | 1 帖 1 单，先到先得 | 1 帖 N 单，可被多人购买 |
| 单笔订单完成/取消/仲裁后的帖子 | 悬赏帖关闭 | 服务帖保持开放，可继续下单 |
| 自己与自己交易 | 禁止接自己的悬赏 | 禁止购买自己的服务 |

交易帖状态为 `OPEN / LOCKED / CLOSED`。悬赏被接单后锁定；悬赏完成或取消后关闭。服务帖允许同时存在多笔订单，单笔订单变化不得关闭整个服务帖。

### 2.2 订单状态与操作规则

| 当前状态 | 操作 | 操作者与前置条件 | 下一状态 | 资金与帖子结果 | 通知 |
|---|---|---|---|---|---|
| — | 发布悬赏 | 学生；余额充足 | `PENDING` | 冻结 buyer 赏金；悬赏帖 `OPEN` | 无 |
| `PENDING` | 接单 | 非帖主学生 | `IN_PROGRESS` | 锁定 seller；悬赏帖 `LOCKED` | 通知 buyer |
| — | 服务下单 | 非帖主学生；余额充足 | `IN_PROGRESS` | 冻结下单者货款；服务帖保持 `OPEN` | 通知 seller |
| `PENDING` | 取消 | 仅 buyer | `CANCELLED` | 解冻退回 buyer；悬赏帖 `CLOSED` | 尚无接单者时不产生对方通知 |
| `IN_PROGRESS` | 取消 | 仅 buyer | `CANCELLED` | 解冻退回 buyer；悬赏帖关闭，服务帖保持开放 | 通知 seller |
| `IN_PROGRESS` | 标记交付 | 仅 seller | `CONFIRMING` | 资金继续冻结 | 通知 buyer |
| `IN_PROGRESS` | 发起申诉 | buyer 或 seller；理由不超过 500 字；无其他 `OPEN` 申诉 | `DISPUTED` | 资金继续冻结；正常交易操作挂起 | 通知对方 |
| `CONFIRMING` | 确认完成 | 仅 buyer | `COMPLETED` | 调用 `settle()`；悬赏帖关闭，服务帖保持开放 | 通知 seller |
| `CONFIRMING` | 发起申诉 | buyer 或 seller；理由不超过 500 字；无其他 `OPEN` 申诉 | `DISPUTED` | 资金继续冻结；确认等操作挂起 | 通知对方 |
| `DISPUTED` | 撤回申诉 | 仅申诉人；申诉为 `OPEN` | 恢复 `from_status` | 申诉置 `WITHDRAWN`；无资金变化 | 通知对方 |
| `DISPUTED` | 仲裁打款 | 仅 ADMIN；申诉为 `OPEN` | `COMPLETED` | 复用 `settle()` 打款给 seller；按交易类型处理帖子 | 通知买卖双方，写审计 |
| `DISPUTED` | 仲裁退款 | 仅 ADMIN；申诉为 `OPEN` | `CANCELLED` | 复用 `unfreeze()` 退款给 buyer；按交易类型处理帖子 | 通知买卖双方，写审计 |
| `COMPLETED / CANCELLED` | 任意交易操作 | 不允许 | 不变 | 不得再次结算、退款或申诉 | 无 |

补充约束：

- 仅 seller 可交付，仅 buyer 可确认或取消；`CONFIRMING` 不允许取消。
- `DISPUTED` 期间，接单、交付、确认、取消全部被拒绝。
- 前端按身份和状态隐藏不可用按钮，后端必须再次校验，不能以按钮隐藏代替权限控制。
- 重复点击、重复请求或状态已变化时，操作应失败并提示刷新，不得产生重复订单、流水或通知。
- 管理端订单监管默认只读；只有申诉仲裁可以改变争议订单的资金归属。

### 2.3 资金与流水规则

| 业务动作 | 可用余额 balance | 冻结金额 frozen | 流水 |
|---|---:|---:|---|
| 模拟充值 | 增加充值金额 | 不变 | 本人一条 `RECHARGE` |
| 发布悬赏、服务下单 | 减少交易金额 | 增加交易金额 | 出资方一条 `FREEZE` |
| 取消、仲裁退款 | 增加交易金额 | 减少交易金额 | 出资方一条 `UNFREEZE` |
| 确认完成、仲裁打款 | buyer 不变；seller 增加交易金额 | buyer 减少交易金额 | buyer 一条 `PAY`，seller 一条 `INCOME` |

共同要求：

1. 金额使用 Java `BigDecimal` 与数据库 `DECIMAL(10,2)`，禁止 `double`，交易金额必须大于 0。
2. 所有资金变动必须写入 `wallet_log`，记录变动后余额、关联订单和时间；不得裸改钱包。
3. 余额不足时整个发布/下单失败，不生成有效订单，不产生部分冻结。
4. 冻结、解冻、结算与订单状态变化位于同一事务，使用悲观锁防止透支和重复结算。
5. 管理员无调账入口；仲裁不得新写资金原语，只能复用 `settle()` / `unfreeze()`。
6. 任意验收时点均应满足：
   **`SUM(wallet.frozen) = PENDING + IN_PROGRESS + CONFIRMING + DISPUTED 状态订单金额合计`**，核对差额为 0。

### 2.4 申诉与举报生命周期

**申诉**：`OPEN → WITHDRAWN` 或 `OPEN → RESOLVED`。申诉记录订单、申诉人、理由、`from_status`、处理结果、裁决管理员、处理意见和时间。一订单最多一条 `OPEN` 申诉；本期只有打款给 seller、退款给 buyer 两种裁决结果。

**举报**：举报对象支持 `POST / TRADE_POST / USER`，初始为 `PENDING`，处理后为 `HANDLED`，结果为 `VALID / REJECTED`。同一举报人对同一对象已有待处理举报时不得重复提交。处理记录处理人、时间、结果和意见；结果通知举报人并写审计日志。

### 2.5 通知与审计事件矩阵

| 事件 | 接收人 | 用户端表现 | 管理端/审计要求 |
|---|---|---|---|
| 悬赏被接单 | buyer | 站内通知，可跳转订单 | 订单详情可见最新状态 |
| 服务被下单 | seller | 站内通知，可跳转订单 | 订单详情可见最新状态 |
| seller 标记交付 | buyer | 站内通知，引导确认 | 订单时间线可见 |
| buyer 确认完成 | seller | 站内通知，可查看收入 | 订单与流水可核对 |
| buyer 取消进行中的订单 | seller | 站内通知 | 订单与退款流水可核对 |
| 对方发起申诉 | 订单另一方 | 站内通知与纠纷提示 | 申诉进入管理端列表 |
| 申诉被撤回 | 订单另一方 | 站内通知，订单恢复原状态 | 申诉记录保留 |
| 仲裁完成 | 买卖双方 | 展示裁决、订单状态和资金结果 | 写 `admin_log` |
| 举报处理完成 | 举报人 | 展示成立/驳回及处理意见 | 写 `admin_log` |
| 封禁、解封、删帖、下架 | 按具体业务处理 | 登录或内容可见性随之变化 | 必须写 `admin_log` |

通知包含类型、内容、关联 `ref_id`、已读状态和创建时间。除表中明确的事件外，不额外承诺消息推送渠道。

### 2.6 内容与封禁的联动边界

- 删除社区帖、下架交易帖后，对应内容不再出现在公共信息流、大厅和搜索结果中；管理端保留治理记录。
- 内容治理不直接修改订单或钱包；订单仍按状态机处理，资金争议只能通过申诉仲裁解决。
- 封禁用户只改变账号可用状态：封禁后无法登录，已签发 token 也不得继续访问受保护接口。
- 封禁不联动删除在架帖子、取消在途订单或修改钱包；解封后账号可重新登录。

### 2.7 双端通用反馈

| 场景 | 产品反馈 |
|---|---|
| 未登录或登录态失效 | 提示重新登录；管理端同时退出受保护页面 |
| 无权限访问 | 阻止页面和接口访问，不展示仅属于另一角色功能 |
| 列表无数据 | 展示明确空态，不将空态当作请求失败 |
| 余额不足 | 保留已填写内容，提示余额不足，不显示发布/下单成功 |
| 订单状态已变化 | 提示状态已更新并刷新详情，不重复执行资金动作 |
| 重复申诉、举报、点赞或评价 | 按共享约束拒绝或去重，不生成重复记录 |
| 请求失败 | 不假定操作成功；恢复可重试状态，并在重试前获取最新数据 |

### 3.2 注册、登录与资料（PB-01、02）

**注册与登录**

- 注册字段：用户名、密码及确认密码；用户名唯一，注册成功后自动创建余额和冻结金额均为 0 的钱包。
- 登录字段：用户名、密码。成功后保存 JWT，后续请求使用 `Authorization: Bearer`。
- 登录响应必须包含 `role`，用户端据此识别 STUDENT/ADMIN；管理员账号进入 `/admin`，学生账号进入用户端。
- 密码仅以后端 BCrypt 哈希保存；学生注册入口不得创建 ADMIN。
- 登录态失效后，交易、钱包和互动操作统一引导重新登录。

**个人资料**

- 可编辑头像、昵称、简介、联系方式；保存后在个人中心和内容展示中使用最新资料。
- 用户名作为登录标识，不在资料编辑中随意修改。

**验收**

1. 使用新用户名注册后可直接登录，并已拥有空钱包；重复用户名注册失败。
2. 登录后可访问学生功能，错误密码、失效 token 不得访问受保护资源。
3. 修改头像、昵称、简介、联系方式并重新进入页面，资料保持为最新值。

### 3.3 钱包（PB-03～05）

**页面内容**

- 钱包概览：可用余额、冻结金额。
- 模拟充值：输入大于 0、最多两位小数的金额，确认后增加可用余额。
- 流水列表：按时间倒序展示类型、金额、变动后余额、备注、关联订单和时间；类型包括充值、冻结、解冻、支出、收入。
- 有关联订单的流水可跳转订单详情；无流水时展示空态。

**验收**

1. 充值后可用余额等额增加，并新增一条 `RECHARGE` 流水。
2. 发布悬赏后可用余额减少、冻结金额等额增加，并新增 `FREEZE`。
3. 取消后冻结资金退回可用余额；确认后 buyer 产生 `PAY`、seller 产生 `INCOME`。
4. 流水顺序、金额、关联订单与订单详情一致。

### 3.4 需求悬赏（PB-06～14）

**发布页字段**

| 字段 | 要求 |
|---|---|
| 标题、描述 | 必填，用于大厅卡片与详情 |
| 赏金 | 必填，大于 0，最多两位小数；发布时校验余额 |
| 分类 | 必填，用于大厅筛选 |
| 图片 | 支持上传并在详情展示 |
| 截止时间 | 必填并在详情展示；当前版本不因此触发自动确认 |

**主流程**

1. 学生充值并填写悬赏，提交后生成 `PENDING` 订单，赏金冻结，悬赏进入大厅。
2. 其他学生在大厅按关键词、分类筛选，仅看到待接单悬赏，进入详情后接单。
3. 接单者成为 seller，订单进入 `IN_PROGRESS`，悬赏锁定。
4. seller 交付后订单进入 `CONFIRMING`；buyer 确认后结算，订单完成。
5. buyer 可在 `PENDING / IN_PROGRESS` 取消并取回冻结资金。

**页面操作**

- 大厅卡片：标题、分类、赏金、图片、截止时间、待接单状态。
- 订单详情：交易帖信息、buyer/seller、金额、当前状态、申诉状态、资金结果和可用操作。
- 当前用户不是订单参与者时，不展示交付、确认、取消、申诉等订单操作。
- 操作成功后同步刷新大厅、个人中心、订单详情和钱包。

**核心验收场景**

- **UC-B01 余额不足**：Given 可用余额小于赏金，When 发布悬赏，Then 发布失败且无有效订单、无资金变动。
- **UC-B02 正常闭环**：Given A 已发布且 B 接单，When B 交付且 A 确认，Then 订单为 `COMPLETED`，A 冻结金额减少、B 可用余额增加，双方流水正确。
- **UC-B03 取消**：Given 订单为 `PENDING` 或 `IN_PROGRESS`，When buyer 取消，Then 订单为 `CANCELLED`，资金全额解冻；非 buyer 或 `CONFIRMING` 状态取消失败。
- **UC-B04 权限与并发**：Given 用户非 seller 或订单已交付，When 重复交付，Then 操作被拒绝且不重复通知；确认/结算同理。
- **UC-B05 禁止自接**：Given 用户查看自己发布的悬赏，When 尝试接单，Then 操作被拒绝。

### 3.5 服务挂牌与下单（PB-15、16）

**发布与购买**

- 挂牌字段：服务标题、价格、描述、分类、图片；发布后状态为待下单，不冻结、不建单。
- 服务市场支持分类浏览、关键词检索和详情查看；开放服务即使已有订单仍可被购买。
- 下单时校验余额并冻结下单者货款，直接创建 `IN_PROGRESS` 订单；帖主为 seller，下单者为 buyer。
- seller 交付、buyer 确认后结算；单笔订单完成、取消或仲裁后，服务帖保持开放。
- 禁止购买自己的服务。

**验收**

1. 挂牌后不产生订单和流水，服务出现在市场。
2. 两个学生可分别购买同一服务，形成两笔独立订单和冻结记录。
3. 任一笔订单完成或取消不影响其他订单，也不阻止后续购买。
4. 余额不足、购买自己的服务或重复无效请求均不得创建异常订单。

### 3.6 个人中心（PB-17）

个人中心提供以下视图：

- **我发布的**：悬赏与服务帖，展示类型、状态和关联订单入口。
- **我发的订单**：当前用户作为 buyer 的订单。
- **我接的单**：当前用户作为 seller 的订单。
- **我的帖子、我的钱包**：进入本人社区内容和钱包页面。

列表状态、详情状态和可用操作必须一致；订单详情只展示当前身份可执行的动作。

### 3.7 社区与找搭子（PB-18～20）

- 发帖支持文字、图片和标签，图片采用本地图片存储；作者可编辑、删除自己的帖子。
- 帖子流按时间倒序展示作者、内容、图片、标签、点赞数和评论信息。
- 点赞以 `(post_id, user_id)` 防重复；重复操作不得重复增加计数。
- 评论支持评论帖子及回复评论，展示作者、内容、回复关系和时间。
- 找搭子使用考研、运动、拼车等标签发布并筛选；标签只是社区帖属性，不创建新的交易类型。
- 被删除或治理的帖子不在公共信息流和搜索中展示。

**验收**：作者可完成发帖、编辑、删除；其他用户可点赞、评论和回复；按标签筛选结果准确；重复点赞不产生第二条记录。

### 3.8 一对一私信（PB-21）

- 提供会话列表和一对一聊天窗口，消息记录发送人、接收人、内容和时间。
- 在线双方通过 WebSocket 实时接收；历史消息在重新进入会话后仍可查看。
- 仅支持两个学生之间私信，不提供群聊和已读回执。
- 消息不得发给不存在的会话对象；连接失败不得把未成功提交的消息显示为已持久化。

### 3.9 全局搜索（PB-22）

- 输入关键词后跨需求悬赏、服务、社区帖检索，结果按三类分组展示。
- 结果项展示类型、标题或内容摘要及详情入口。
- 已删除、下架或不可公开的内容不得进入结果。
- 无结果时展示空态；关键词与悬赏大厅、服务市场的筛选口径保持一致。

### 3.10 站内通知（PB-23）

- 通知列表展示内容、时间、已读/未读状态，支持查看并标记已读。
- 有 `ref_id` 的通知可跳转对应订单或内容；目标已不可见时展示状态说明，不出现空白页。
- 接单、下单、交付、确认、取消、申诉、撤回、仲裁和举报处理按 2.5 节生成通知。

### 3.11 交易互评（PB-24）

- 仅 `COMPLETED` 订单的 buyer、seller 可分别提交文字评价。
- 每个用户对同一订单最多评价一次，以 `(order_id, from_user_id)` 防重复。
- 双方评价在订单详情展示；未完成、已取消或无关用户不能评价。
- 当前版本只有文字互评，不由互评自动计算信用分。

### 3.12 订单申诉（PB-32、38）

**入口与流程**

1. buyer 或 seller 在 `IN_PROGRESS / CONFIRMING` 订单详情点击申诉，填写不超过 500 字的理由。
2. 提交成功后创建 `OPEN` 申诉，订单转为 `DISPUTED`，详情展示纠纷横幅并禁用正常交易操作。
3. 仅申诉人可撤回；撤回后申诉为 `WITHDRAWN`，订单恢复 `from_status`。
4. 管理员处理后，订单详情展示裁决结果、处理意见、最终状态和对应资金结果。

**核心验收场景**

- **UC-A01 挂起**：Given 订单为 `CONFIRMING`，When seller 申诉成功，Then 订单为 `DISPUTED`，buyer 确认和双方取消均失败。
- **UC-A02 撤回**：Given 当前用户是申诉人，When 撤回 `OPEN` 申诉，Then 恢复 `CONFIRMING`，可继续按状态机操作；非申诉人撤回失败。
- **UC-A03 重复申诉**：Given 订单已有 `OPEN` 申诉，When 任一方再次申诉，Then 操作被拒绝。
- **UC-A04 裁决可见**：Given 管理员已裁决，When 双方查看订单，Then 双方看到一致的结果、状态、通知和流水。

### 3.13 举报（PB-35、38）

- 社区帖、交易帖、用户详情提供举报入口，填写原因后提交，举报状态为 `PENDING`。
- 同一用户对同一对象已有待处理举报时，提示已提交且处理中，不重复创建。
- 举报处理后，举报人收到成立/驳回、处理人及处理意见通知。
- 举报提交不直接删帖、下架或封禁；只有管理员处理后才发生治理动作。

## 四、管理员端产品规格

> 开发责任：管理员端开发成员。
> 本章涵盖 PB-25、PB-31、PB-33～PB-38，以及 PB-32、PB-35 中属于平台侧的内容。

### 4.1 入口、布局与权限（PB-38）

- 管理员通过统一登录获得带 `role=ADMIN` 的登录响应，进入独立 `/admin` 布局。
- 前端路由守卫仅允许 ADMIN；后端 `/api/admin/**` 统一执行 `hasRole("ADMIN")`，前端守卫不能替代后端鉴权。
- 管理员账号由启动引导初始化，不通过学生注册页创建。
- 主导航固定为：仪表盘、订单管理、申诉仲裁、举报处理、用户管理、资金监管、审计日志。
- 学生 token 访问管理页面或接口时被拒绝；封禁学生的已有 token 同样失效。

### 4.2 仪表盘（PB-31）

| 组件 | 指标口径 |
|---|---|
| 用户数 | STUDENT 用户总数 |
| 订单数 | 全部 `trade_order` 数量 |
| GMV | `COMPLETED` 订单金额合计 |
| 冻结总额 | 全部钱包 `frozen` 合计 |
| 待办 | `OPEN` 申诉数 + `PENDING` 举报数 |
| 订单状态分布 | 六态订单当前数量，使用饼图 |
| 近 7 天趋势 | 含今天在内的连续 7 天订单创建量，无订单日期补 0，使用折线图 |

**交互与验收**

- 页面进入时加载全部指标；加载失败展示失败状态，不以 0 冒充真实数据。
- 看板数值与订单管理、申诉、举报、资金监管的同口径查询结果一致。
- 新增订单、完成订单、发起申诉或处理举报后，重新查询应反映最新数据。
- 图表使用 ECharts，卡片、饼图和折线均展示明确单位与空数据状态。

### 4.3 订单管理（PB-33）

**列表**

- 支持按状态、交易类型、buyer、seller、创建时间筛选。
- 展示订单号、类型、交易帖、buyer/seller、金额、状态和创建时间。
- 支持查看全部订单，不仅限于当前管理员处理的订单。

**详情时间线**

- 聚合订单、交易帖、买卖双方、关联资金流水和申诉记录。
- 时间线按时间展示创建/接单或下单、交付、确认、取消、申诉、撤回、仲裁及资金事件。
- 订单页保持只读，不提供直接改状态、改金额或调账按钮；争议订单从申诉详情进入仲裁。

**验收**：筛选结果准确；详情能解释订单当前状态与每笔资金流向；无权限学生无法调用对应管理接口。

### 4.4 申诉仲裁（PB-32）

**列表与详情**

- `OPEN` 申诉优先展示，可查看申诉人、订单、理由、`from_status`、当前状态和提交时间。
- 详情同时展示买卖双方、金额、订单时间线和关联流水，辅助裁决。

**处理规则**

1. 仅 `OPEN` 且订单为 `DISPUTED` 的申诉可裁决，管理员必须填写处理意见。
2. **打款给 seller**：结果 `RELEASE_TO_SELLER`，调用 `settle()`，订单 `COMPLETED`。
3. **退款给 buyer**：结果 `REFUND_TO_BUYER`，调用 `unfreeze()`，订单 `CANCELLED`。
4. 裁决前进行二次确认；成功后申诉置 `RESOLVED`，记录 outcome、管理员、意见和时间。
5. 按交易类型处理帖子：悬赏关闭，服务帖保持开放；通知双方并写审计。
6. 已撤回、已处理或订单状态不符时拒绝裁决，不得重复结算。

**核心验收场景**

- **AC-R01 打款**：仲裁前 buyer 冻结金额包含订单款；仲裁后 seller 等额入账，双方各有正确流水，订单完成。
- **AC-R02 退款**：仲裁后 buyer 冻结金额减少、可用余额等额增加，订单取消，seller 不增加收入。
- **AC-R03 防重复**：对同一申诉再次裁决失败，无额外流水、通知或余额变化。
- **AC-R04 资金守恒**：两种裁决后平台冻结总额与在途订单金额差额仍为 0。

### 4.5 举报处理（PB-25、35）

- 列表优先展示 `PENDING`，支持按状态、对象类型查看举报；详情展示举报人、对象、原因和提交时间。
- 处理时填写结果与意见；处理人、处理时间自动记录。
- 举报成立时可一键联动匹配动作：社区帖删帖、交易帖下架、用户封禁；对象类型与动作不匹配时不得执行。
- 举报驳回时不执行联动治理；两种结果都必须通知举报人并写审计。
- 已处理举报不得重复处置，防止重复删帖、封禁或写多条结果。

**验收**：成立、驳回两条路径均有处理结果和通知；联动后用户端公共列表不再展示被删/下架内容；审计可追溯到管理员和目标对象。

### 4.6 内容治理动作（PB-25）

内容治理不新增第 8 个主页面，入口位于举报处理及相关详情：

- 删除违规社区帖、下架违规交易帖前展示对象摘要并进行二次确认。
- 成功后用户端大厅、信息流、搜索同步排除目标内容；管理端保留记录。
- 内容动作不直接取消订单或修改钱包；相关交易仍按订单状态机处理。
- 每次删帖、下架均写审计日志，包含管理员、目标类型、目标 ID、动作和时间。

### 4.7 用户管理（PB-25、37）

- 用户列表展示用户名、昵称、角色、状态、注册时间，支持按用户和状态查询。
- 管理员可封禁或解封，执行前展示账号及影响说明并二次确认。
- 封禁后该用户无法重新登录，已有 token 立即失去受保护接口访问能力。
- 封禁不删除帖子、不取消订单、不调整钱包；已有纠纷仍可被管理员裁决。
- 解封后允许重新登录；封禁、解封均写审计。

**验收**：被封禁学生的旧 token 和新登录均失败，但其订单、帖子和钱包数据未被误改；解封后登录恢复。

### 4.8 资金监管（PB-34）

**查询能力**

- 按用户查询钱包可用余额、冻结金额和全部流水。
- 查询全平台流水，支持按用户、流水类型、订单和时间筛选。
- 展示平台冻结总额、在途订单应冻金额和差额；在途状态为 `PENDING / IN_PROGRESS / CONFIRMING / DISPUTED`。

**边界与验收**

- 页面只读，不提供充值、扣款、调账、删除流水等入口。
- 正常发布、取消、结算、仲裁打款和仲裁退款后，差额均为 0。
- 若差额非 0，页面如实显示异常，不自动修数或掩盖差额。
- 订单详情中的流水与资金监管查询结果一致。

### 4.9 审计日志（PB-36）

- 封禁、解封、删帖、下架、处理举报、仲裁均写入 `admin_log`。
- 列表支持按管理员、动作、时间筛选，展示目标类型、目标 ID、关键处理详情和创建时间。
- 日志只增不改不删，页面不提供编辑、删除入口。
- 仲裁日志需能关联订单和裁决结果；举报日志需能关联举报及联动动作。

**验收**：完成每类管理动作后均能查到一条对应日志；筛选准确；任何管理员都不能通过后台修改或删除历史日志。

## 五、双端分工与跨端协作

### 5.1 开发责任表

| 工作项 | 用户端开发成员 | 管理员端开发成员 | 共同确认 |
|---|---|---|---|
| 登录与角色 | 注册、学生登录、学生路由 | 管理登录、AdminLayout、管理路由守卫 | `LoginResp.role`、JWT、后端 ADMIN 鉴权 |
| 交易与钱包 | 发布、接单/下单、交付、确认、取消、钱包展示 | 只读订单视图、流水与冻结监管 | buyer/seller、六态、金额、事务、流水口径 |
| 社区与搜索 | 发帖、点赞、评论、找搭子、私信、搜索 | 删帖/下架后的治理结果查询 | 内容状态与公共可见性 |
| 申诉 | 发起、撤回、纠纷提示、结果展示 | 列表、详情、打款/退款裁决 | `OPEN/WITHDRAWN/RESOLVED`、`from_status`、资金结果 |
| 举报 | 提交、待处理去重、结果通知 | 受理、成立/驳回、联动治理 | 对象类型、结果、处理人、意见 |
| 用户封禁 | 登录失效与重新登录表现 | 封禁/解封及审计 | 旧 token 失效，不联动帖/单/钱包 |
| 通知 | 列表、已读、关联跳转 | 处理动作触发通知 | 2.5 节事件、接收人和 `ref_id` |
| 部署与测试 | 用户端场景、接口与页面自测 | 管理端场景、权限与页面自测 | PB-26、PB-27 及跨端回归 |

具体成员姓名由项目组填入团队分工表；本章作为两端责任边界，不虚构人员安排。

### 5.2 跨端数据契约

| 数据 | 用户端产出/消费 | 管理员端产出/消费 | 必须一致的字段 |
|---|---|---|---|
| 登录响应 | 消费学生登录 | 消费管理员登录 | token、role |
| 订单详情 | 产出交易动作并消费最新状态 | 消费全量订单并展示时间线 | type、status、buyer、seller、amount、post |
| 申诉 | 产出 OPEN/WITHDRAWN，消费 RESOLVED | 消费 OPEN，产出 RESOLVED | from_status、outcome、admin、意见、时间 |
| 钱包与流水 | 消费本人钱包和流水 | 消费全量只读数据 | balance、frozen、type、balance_after、order_id |
| 举报 | 产出 PENDING，消费 HANDLED | 消费 PENDING，产出 HANDLED | target_type、target_id、result、handler、意见 |
| 通知 | 消费并展示 | 管理动作触发部分通知 | type、content、ref_id、is_read、created_at |

除已有 `/api/admin/**` 和 `/admin` 边界外，具体 URL、请求 DTO 和字段序列由两端在接口设计中共同确认，但不得改变本文的业务含义。

### 5.3 必做双端联调链

1. **举报闭环**：学生举报 → 管理端待处理可见 → 成立并联动处置/驳回 → 学生收到结果 → 内容或账号状态正确 → 审计完整。
2. **申诉打款**：学生申诉 → 订单 `DISPUTED` 且学生操作挂起 → 管理员打款 → seller 收款、订单完成 → 双方通知 → 资金差额为 0。
3. **申诉退款**：学生申诉 → 管理员退款 → buyer 收到退款、订单取消 → 双方通知 → 服务帖不被误关 → 资金差额为 0。
4. **申诉撤回**：申诉人撤回 → 恢复 `from_status` → 学生正常操作恢复 → 管理端不可再裁决该申诉。
5. **封禁与解封**：管理员封禁 → 学生旧 token 失效且不能登录 → 帖子、订单、钱包保持原状 → 解封后恢复登录。
6. **监管一致性**：学生完成发布、取消、结算 → 管理端订单时间线、流水和冻结核对同步正确。

## 六、非功能与质量要求

### 6.1 安全与权限

- 密码使用 BCrypt；登录采用无状态 JWT。
- 所有受保护接口执行后端身份与订单参与者校验，`/api/admin/**` 额外强制 ADMIN。
- 管理路由守卫用于体验，不作为安全边界；学生直接请求管理接口必须失败。
- 封禁校验对已有 token 生效。

### 6.2 数据与一致性

- 金额统一 `DECIMAL(10,2)` / `BigDecimal`，时间统一 `LocalDateTime`，数据库使用 MySQL 8 utf8mb4。
- 资金与订单操作使用事务和悲观锁；余额不足、状态冲突时整体回滚。
- 用户名、一人一个钱包、点赞、评价使用唯一约束；待处理举报和 `OPEN` 申诉由服务层去重。
- 所有接口返回统一 `ApiResponse<T>`；业务失败不得返回虚假的成功页面状态。

### 6.3 通信与部署

- 私信使用 WebSocket 一对一实时通信，消息同时持久化以支持历史查看。
- Sprint 1 可用 Docker Compose 启动本地 MySQL；Sprint 2 完成后端、前端镜像和 Compose 一键启动。
- CodeArts 托管与部署记录随 Sprint 2 交付。

### 6.4 测试要求（PB-27）

核心领域逻辑使用单元测试，关键业务流程使用接口测试和端到端走查，至少覆盖：

- 钱包：充值、余额不足、冻结、解冻、结算、重复操作、并发安全。
- 订单：六态流转、参与者权限、禁止自交易、服务一帖多单、帖子状态联动。
- 仲裁：打款/退款、撤回、重复裁决、DISPUTED 挂起、资金守恒。
- 权限：学生访问管理接口、非 ADMIN 路由、封禁后旧 token。
- 社区与举报：点赞/评价唯一、举报去重、处置联动与通知。
- Sprint 3 的双端测试作为整体验收质量门禁，不改变 PB-27 在 Backlog 中的 S1/S2 归属。

## 七、分阶段验收标准

| 阶段 | 必走通的端到端场景 | 通过条件 |
|---|---|---|
| Sprint 1 | 注册 → 充值 → 发布悬赏（冻结）→ 接单 → 交付 → 确认（结算） | 用户端订单、钱包、流水与共享六态规则一致；另验收 PENDING、IN_PROGRESS 取消 |
| Sprint 2 | 挂牌 → 多人下单（冻结）→ 交付 → 确认；发帖 → 点赞/评论 → 找搭子 → 私信 | 服务一帖多单不互相影响；搜索、通知、互评可用；基础治理有效；Docker 一键启动 |
| Sprint 3 | 举报 → 处理 → 通知；申诉 → 挂起 → 仲裁打款/退款 → 通知与审计 | 7 个管理主页面可用；权限隔离、资金差额为 0、日志只增不改；双端联调链全部通过 |

答辩演示至少保留：六态订单状态、资金守恒、服务一帖多单、仲裁打款与退款、举报闭环、封禁后旧 token 失效的证据。
