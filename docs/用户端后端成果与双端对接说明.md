## 4. 用户前端统一对接约定

### 4.1 地址与认证

- 后端基础地址：`http://localhost:8080`
- 业务接口前缀：`/api`
- 推荐用户前端通过 Vite 将 `/api` 代理到 `http://localhost:8080`。
- 除 `/api/auth/**` 外，当前接口都需要登录。
- 登录后在请求头携带：

```http
Authorization: Bearer <token>
Content-Type: application/json
```

当前没有独立 CORS 配置。若前端不通过同源代理而直接跨域访问，需要后端另行增加 CORS 配置。

### 4.2 统一响应

所有业务响应采用：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

| 情况 | HTTP 状态 | 业务 code | 前端处理 |
|---|---:|---:|---|
| 成功 | 200 | 0 | 读取 `data` |
| 业务失败或参数校验失败 | 200 | 通常为 40000 | 展示 `message`，不能当作成功 |
| 未登录或 token 无效 | 401 | 40100 | 清理登录态并跳转登录页 |
| 未捕获服务器异常 | 200 | 50000 | 提示服务器错误并记录联调信息 |

**axios 响应拦截器必须同时检查 HTTP 状态和业务 `code`，不能只判断 HTTP 200。**

### 4.3 字段与精度

- ID 为数值，前端应保存原始 ID，不要自行转换成浮点金额。
- 金额对应后端 `BigDecimal`，数据库为 `DECIMAL(10,2)`；金额必须大于 0，最多两位小数。
- 时间字段采用 ISO 本地日期时间格式，例如 `2026-12-31T18:00:00`，不带 `Z`。
- 当前列表均直接返回数组，未分页。
- `images` 当前是字符串字段，设计为逗号分隔的本地图片路径；**图片上传接口尚未实现**。

## 5. 账户接口

### 5.1 注册

```http
POST /api/auth/register
```

无需 token。

请求：

```json
{
  "username": "student01",
  "password": "123456",
  "confirmPassword": "123456",
  "nickname": "同学甲"
}
```

| 字段 | 规则 |
|---|---|
| username | 必填，4–20 位，唯一 |
| password | 必填，6–32 位 |
| confirmPassword | 必填，必须与 password 一致 |
| nickname | 可选，最多 20 字；空值时使用 username |

成功时 `data` 为新用户 ID。注册成功后用户默认 `role=STUDENT`、`status=ACTIVE`，同时创建余额和冻结金额均为 0 的钱包。

### 5.2 登录

```http
POST /api/auth/login
```

请求：

```json
{
  "username": "student01",
  "password": "123456"
}
```

成功响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "token": "<JWT>",
    "userId": 1,
    "nickname": "同学甲",
    "role": "STUDENT"
  }
}
```

前端建议持久化 `token`、`userId`、`nickname` 和 `role`。其中 `role` 可用于页面展示和路由提示，**不能替代后端管理员权限校验**。

## 6. 钱包接口

### 6.1 查询本人钱包

```http
GET /api/wallet
```

`data`：

| 字段 | 含义 |
|---|---|
| id | 钱包 ID |
| userId | 当前用户 ID |
| balance | 可用余额 |
| frozen | 冻结金额 |

### 6.2 模拟充值

```http
POST /api/wallet/recharge
```

```json
{
  "amount": 100.00
}
```

成功后返回最新钱包，并新增一条 `RECHARGE` 流水。这是模拟充值，不涉及真实支付。

### 6.3 查询本人流水

```http
GET /api/wallet/logs
```

返回按 ID 倒序排列的流水数组：

| 字段 | 含义 |
|---|---|
| id | 流水 ID |
| userId | 钱包所属用户 |
| type | RECHARGE / FREEZE / UNFREEZE / PAY / INCOME |
| amount | 带符号金额，正数为入账语义，负数为出账语义 |
| balanceAfter | 变动后的**可用余额**，不是余额加冻结金额 |
| orderId | 关联订单；充值时为空 |
| remark | 备注 |
| createdAt | 创建时间 |

资金类型对照：

| 类型 | 可用余额 | 冻结金额 | 流水用户 |
|---|---|---|---|
| RECHARGE | 增加 | 不变 | 充值人 |
| FREEZE | 减少 | 增加 | buyer |
| UNFREEZE | 增加 | 减少 | buyer |
| PAY | 不变 | 减少 | buyer |
| INCOME | 增加 | 不变 | seller |

## 7. 悬赏与订单接口

### 7.1 发布悬赏

```http
POST /api/trade/posts
```

```json
{
  "title": "帮取快递",
  "description": "菜鸟驿站取件后送到宿舍",
  "images": "",
  "price": 5.00,
  "category": "跑腿",
  "deadline": "2026-12-31T18:00:00"
}
```

| 字段 | 规则 |
|---|---|
| title | 必填，最多 80 字 |
| description | 必填，最多 1000 字 |
| images | 可选，最多 500 字；当前直接保存字符串 |
| price | 必填，大于 0，最多两位小数 |
| category | 必填，最多 30 字 |
| deadline | 必填；当前不会据此自动确认订单 |

成功时 `data` 为帖子 ID。后端在同一事务中：

1. 创建 `OPEN / BOUNTY` 帖子；
2. 创建 `PENDING` 订单，`buyerId=发布者`、`sellerId=null`；
3. 冻结发布者赏金并写 `FREEZE` 流水；
4. 任一步失败则整体回滚。

### 7.2 悬赏大厅

```http
GET /api/trade/posts?type=BOUNTY&category=跑腿&keyword=快递
```

三个查询参数均可选：

- `type`：当前传 `BOUNTY`；
- `category`：分类精确匹配；
- `keyword`：标题模糊搜索，不搜索描述。

结果只包含 `OPEN` 帖子，按 ID 倒序返回。接单后的 `LOCKED` 帖子和结束后的 `CLOSED` 帖子不会出现在大厅。

### 7.3 帖子与订单详情

```http
GET /api/trade/posts/{postId}
```

`data` 结构：

```json
{
  "post": {
    "id": 1,
    "publisherId": 10,
    "type": "BOUNTY",
    "title": "帮取快递",
    "description": "菜鸟驿站取件后送到宿舍",
    "images": "",
    "price": 5.00,
    "category": "跑腿",
    "deadline": "2026-12-31T18:00:00",
    "status": "LOCKED",
    "createdAt": "2026-11-11T10:00:00"
  },
  "order": {
    "id": 2,
    "postId": 1,
    "buyerId": 10,
    "sellerId": 11,
    "amount": 5.00,
    "status": "IN_PROGRESS",
    "createdAt": "2026-11-11T10:00:00",
    "updatedAt": "2026-11-11T10:05:00"
  }
}
```

已取消订单也会返回，前端可以正常展示 `CANCELLED`。当前没有独立的 `/orders/{id}` 查询接口；只有订单 ID 时，可先通过个人中心数据取得 `postId`，再查询本接口。

### 7.4 订单操作

以下接口均无请求体，成功时 `data` 为最新订单：

| 方法 | 路径 | 操作者与前置状态 | 资金与帖子结果 |
|---|---|---|---|
| POST | `/api/trade/orders/{orderId}/accept` | 非 buyer；PENDING | seller 锁定为当前用户；订单 IN_PROGRESS；帖子 LOCKED |
| POST | `/api/trade/orders/{orderId}/deliver` | 仅 seller；IN_PROGRESS | 订单 CONFIRMING；资金继续冻结 |
| POST | `/api/trade/orders/{orderId}/confirm` | 仅 buyer；CONFIRMING | 调用结算；订单 COMPLETED；帖子 CLOSED |
| POST | `/api/trade/orders/{orderId}/cancel` | 仅 buyer；PENDING 或 IN_PROGRESS | 解冻退款；订单 CANCELLED；帖子 CLOSED |

前端按钮显示建议：

| 条件 | 显示操作 |
|---|---|
| 订单 PENDING，且当前用户不是 buyer | 接单 |
| 当前用户是 seller，且订单 IN_PROGRESS | 标记交付 |
| 当前用户是 buyer，且订单 CONFIRMING | 确认完成 |
| 当前用户是 buyer，且订单 PENDING / IN_PROGRESS | 取消 |

按钮隐藏只是体验优化，后端仍会重新校验身份和状态。重复点击或状态已变化时会返回业务错误，前端应刷新详情，不应假定操作成功。

每次接单、交付、确认或取消成功后，建议同时刷新：

- 订单详情；
- 个人中心；
- 悬赏大厅；
- 钱包与流水。

### 7.5 个人中心

```http
GET /api/trade/orders/mine
```

`data`：

```json
{
  "asBuyer": [],
  "asSeller": [],
  "published": []
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| asBuyer | TradeOrder[] | 当前用户发布悬赏后形成的订单 |
| asSeller | TradeOrder[] | 当前用户接取的订单 |
| published | TradePost[] | 当前用户发布的悬赏帖，含 OPEN / LOCKED / CLOSED |

三组数据均只根据当前 token 用户查询，并按 ID 倒序返回。

## 8. 核心数据模型

### 8.1 状态枚举

```text
PostType:    BOUNTY | SERVICE（预留）
PostStatus:  OPEN | LOCKED | CLOSED
OrderStatus: PENDING | IN_PROGRESS | CONFIRMING | DISPUTED（预留） | COMPLETED | CANCELLED
User.role:   STUDENT | ADMIN
User.status: ACTIVE | BANNED
```

悬赏状态机：

```text
发布：无 → PENDING，帖子 OPEN，冻结 buyer 赏金
接单：PENDING → IN_PROGRESS，帖子 LOCKED
交付：IN_PROGRESS → CONFIRMING，帖子保持 LOCKED
确认：CONFIRMING → COMPLETED，帖子 CLOSED，结算给 seller
取消：PENDING / IN_PROGRESS → CANCELLED，帖子 CLOSED，退款给 buyer
```

### 8.2 数据表关系

| 表 | 关键字段 | 逻辑关系 |
|---|---|---|
| t_user | id、username、role、status | 一个用户对应一个钱包 |
| wallet | user_id、balance、frozen | wallet.user_id → t_user.id |
| wallet_log | user_id、type、amount、balance_after、order_id | 记录全部资金变化 |
| trade_post | publisher_id、type、price、status | trade_post.publisher_id → t_user.id |
| trade_order | post_id、buyer_id、seller_id、amount、status | 当前 BOUNTY 一帖一单 |

当前 DDL 使用逻辑关联和索引，没有声明数据库外键。管理端编写查询时可以直接按上述 ID 字段 JOIN，但不能假定数据库会替业务层保证引用完整性。

### 8.3 资金规则

- 所有资金变化必须由 `WalletService` 完成并写 `wallet_log`。
- 订单状态变化和资金变化处于同一事务。
- 订单操作使用订单行悲观锁，资金操作使用钱包行悲观锁。
- 不允许通过直接 UPDATE 钱包表实现确认、取消或仲裁。
- 业务不变量：

```text
所有钱包 frozen 总额
= PENDING + IN_PROGRESS + CONFIRMING + DISPUTED 订单金额总额
```

## 9. 管理员端开发对接建议

### 9.1 当前尚未提供的管理能力

当前后端没有 `/api/admin/**` 接口，也没有管理员订单列表、资金看板、申诉仲裁、举报、审计日志或用户管理接口。

管理员端成员需要新增独立的管理接口与权限控制，不能把用户端接口直接当作管理接口使用。特别注意：

- 当前 JWT 安全链只要求“已登录”，没有基于 `ADMIN` 角色的接口授权；
- 登录响应中的 `role` 只是数据字段，不构成管理员权限；
- 注册接口只创建 STUDENT，不提供管理员注册入口；
- 当前封禁校验发生在登录时，已签发 token 的实时封禁拦截尚未实现，封禁功能上线前必须补齐；
- 管理员不得新增直接调账接口，后续仲裁必须复用订单与钱包领域规则。

### 9.2 管理端可复用的数据与规则

管理端订单视图可基于 `trade_order` 关联 `trade_post`、`t_user`；资金视图可基于 `wallet` 和 `wallet_log`。

冻结总额核对可参考以下只读 SQL（这是开发建议，不是现有接口）：

```sql
SELECT
    wallet_totals.frozen_total,
    order_totals.in_transit_total,
    wallet_totals.frozen_total - order_totals.in_transit_total AS difference
FROM (
    SELECT COALESCE(SUM(frozen), 0.00) AS frozen_total
    FROM wallet
) AS wallet_totals
CROSS JOIN (
    SELECT COALESCE(SUM(amount), 0.00) AS in_transit_total
    FROM trade_order
    WHERE status IN ('PENDING', 'IN_PROGRESS', 'CONFIRMING', 'DISPUTED')
) AS order_totals;
```

正常业务状态下 `difference` 应为 0。管理端只读看板可以使用该核对思路，但不能据此直接修补钱包数据。

后续 Sprint 3 仲裁建议保持以下边界：

- 只允许争议订单进入仲裁流程；
- 判 seller 胜时复用 `settle()`；
- 判 buyer 胜时复用 `unfreeze()`；
- 订单、资金、申诉结果和审计日志在同一业务事务中协调；
- 不创建另一套订单状态机，不开放管理员手工修改余额。

### 11.2 联调前必须了解的限制

1. 自动化测试使用 H2，真实 MySQL 仍需独立联调。
2. 当前没有真实并发测试；悲观锁已实现，但后续应补多线程回归测试。
3. 尚未增加跨钱包、跨订单的冻结总额聚合自动化测试。
4. `deliver` / `confirm` 的错误消息差异可能让非参与者推断订单状态，后续可统一权限错误。
5. `settle()` 固定先锁 buyer 再锁 seller；极端互逆订单并发确认存在理论死锁风险，后续应统一按用户 ID 排序加锁。
6. 列表未分页，数据量增长后需增加分页参数。
7. 当前没有图片上传、站内通知、资料编辑、服务挂牌、社区、私信、评价和管理接口；这些属于后续 Sprint，不要在本阶段误判为接口遗漏。
