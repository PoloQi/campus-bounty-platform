# 校园悬赏平台 · Sprint 3 实现计划（用户后端：学生侧）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不改动 S1/S2 学生侧既有功能的前提下，交付 Sprint 3 **学生侧后端**：申诉发起/撤回/查询（订单 DISPUTED 挂起）、学生举报接口迁移与去重、`/api/admin/**` 统一 ADMIN 鉴权、封禁后已签发 token 立即失效。**不包含**管理员仲裁、举报处置、订单/资金查询、看板、审计日志——这些由管理端成员在总计划 `2026-10-11-sprint3-管理保障.md` 的 Task 2/4/5/6/7/8/11 中实现。

**Architecture:** 沿用 Spring Boot 单体分层。新增 `trade.Appeal` 聚合 + `AppealService`（open/withdraw/viewOpen），通过 `TradeOrderRepository.findByIdForUpdate` 悲观锁保证状态变更与去重的原子性；**不改 `TradeOrderService` 的任何流转代码**——`DISPUTED` 不在 accept/deliver/confirm/cancel 的状态白名单内，挂起由既有校验天然实现，用测试钉死。学生举报接口由 `POST /api/admin/reports` 迁至 `POST /api/reports`，`/api/admin/**` 统一 `hasRole("ADMIN")`。仲裁由管理端在 `AppealService` 上做加法（`t_appeal` 字段一次性建全）。

**Tech Stack:** 沿用仓库实际版本：Java 17 · Spring Boot **4.1.2** · Spring Data JPA · MySQL 8（生产，`ddl-auto=validate` + 手写 schema.sql）· H2 MySQL 兼容模式（测试）· jjwt 0.12.3 · Lombok。

**Spec:** `docs/superpowers/specs/2026-10-11-管理保障模块-设计.md`（§4 申诉、§5.3 举报去重、§9 封禁、§11 权限）；PRD `docs/校园悬赏平台-产品需求文档-PRD.md`（§2.2 状态机、§2.5 通知、§3.12 申诉、§3.13 举报、§4.1 权限）；总计划 `docs/superpowers/plans/2026-10-11-sprint3-管理保障.md`（本计划只取其学生侧部分，并按真实代码修正偏差）。

## Global Constraints

- 承接 S1/S2 全部约束：包根 `com.campus.bounty`；统一响应 `ApiResponse<T>`；业务错误抛 `BizException`（默认 code=40000，HTTP 200 返回业务错误码）；金额 `BigDecimal`；时间 `LocalDateTime`；JWT 无状态；测试用 `@SpringBootTest + @ActiveProfiles("test")` + H2。
- 后端模块目录为 **`campus-bounty-user-backend/`**（不是总计划中的 `backend/`）。Maven 命令使用 `./mvnw.cmd -q test ...`。
- **不改 `OrderStatus` 枚举**（`DISPUTED` 已预留）；**不改 `TradeOrderService`**；新表只加 `t_appeal`（含 `outcome/admin_id/admin_comment/handled_at`，为管理端仲裁预留，避免后续改表）。
- **资金红线**：本分支不触碰钱包逻辑；仲裁资金由管理端复用 `WalletService.settle/unfreeze`。
- **HTTP 状态码约定**：未认证（含无效/封禁 token）→ 401（`SecurityConfig.authenticationEntryPoint`）；已认证但非 ADMIN 访问 `/api/admin/**` → 403；业务失败 → HTTP 200 + `ApiResponse.code=40000/40300`。
- 返回学生侧数据禁止泄露 `passwordHash`。
- 注释只写「为什么」；每个 Task 结束可截图/可演示。

## Review Focus

1. **DISPUTED 挂起被绕过**：进入 DISPUTED 后 accept/deliver/confirm/cancel 必须全部抛 `BizException`（依赖既有状态白名单）。→ Task 2 `disputed_blocks_normal_flows`。
2. **重复申诉/重复撤回**：并发下第二事务必须失败——靠订单行悲观锁串行化，而非先查后改。→ Task 2 `open_rejects_*` / `withdraw_*`。
3. **封禁不即时生效**：BANNED 用户的有效 JWT 必须立即无法访问受保护接口。→ Task 1 `banned_token_is_rejected`（断言 401）。
4. **权限收口误伤既有测试**：`AdminServiceTest` 中学生调用管理接口原断言 body `code=40300`，安全链收口后应在过滤器层返回 HTTP 403，必须同步修改。→ Task 1 Step 7。
5. **申诉查询越权**：非订单参与者不得查询/操作申诉。→ Task 2 `viewOpen` 校验 + HTTP 用例。

- [ ] **Step 4: AppealService（发起/撤回/查看）**

`open`：理由非空且 ≤500 字 → 锁订单行 → 状态须为 IN_PROGRESS/CONFIRMING → 操作者须为 buyer/seller → 不得已有 OPEN → 写 Appeal（fromStatus=当前状态）→ 订单置 DISPUTED → 通知对方 APPEAL_CREATED。

`withdraw`：仅 OPEN、仅申诉人 → 锁订单行确认仍 DISPUTED → 订单恢复 from_status → 申诉 WITHDRAWN + handledAt → 通知对方 APPEAL_WITHDRAWN。

`viewOpen`：非交易双方拒绝；无 OPEN 返回 null。

并发靠 `findByIdForUpdate` 串行化：重复 open 的第二事务看到 DISPUTED 失败；重复 withdraw 的第二事务看到订单已恢复失败。
