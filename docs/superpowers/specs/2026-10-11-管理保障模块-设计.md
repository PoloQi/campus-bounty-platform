# 校园悬赏平台 · 管理保障模块设计（主设计规格 · 补充篇）

> 版本：v1.0 ｜ 日期：2026-10-11 ｜ 状态：待用户评审
> 主规格：`docs/superpowers/specs/2026-10-11-校园悬赏平台-设计.md`
> 定位：本篇是主规格的**补充**，只做加法——不删减、不改变任何已定功能（WebSocket 私信等原样保留），
> 新增「管理保障」子系统，并据此把总工期由 8 周调整为 **11 周（新增 Sprint 3，3 周）**。

---

## 1. 背景与问题

改版后的平台以「模拟余额 + 冻结托管 + 担保结算」为核心卖点：钱在交易过程中押在平台。
这天然带来平台的**担保责任**——交易双方出现争议时，平台必须有裁决出口；资金在平台手里，
平台必须有审计与核对手段。

而现有设计中，管理员能力只有「删帖 / 下架 / 封禁」（Sprint 2 Task 10，7h），存在四个断点：

1. **纠纷无出口**：订单状态机 5 态中无纠纷状态。买方在待确认阶段拒不确认、交付有争议时，
   钱会一直冻结，没有任何机制推动到终态。
2. **举报无闭环**：`t_report` 只有 `PENDING/HANDLED`，无处理结果、无处理人、举报人收不到反馈。
3. **资金与订单无管理视图**：后台看不到全量订单、在途托管资金、用户流水。
4. **管理动作无留痕**：封禁、下架、动钱均无审计记录。

本模块把主规格 §3 的「④ 治理」从**内容治理**升级为
**交易保障 + 内容治理 + 资金监管 + 运营可视**四位一体的管理后台。

## 2. 范围与非目标

**范围内（Sprint 3 交付）**：

- 纠纷申诉与管理员仲裁（订单状态机加 `DISPUTED` 分支）
- 举报处理完整闭环
- 管理员订单视图（全量筛选 + 详情时间线）
- 资金托管监管（钱包/流水查询 + 冻结总额核对）
- 数据看板（指标卡 + 状态分布 + 近 7 天趋势）
- 用户封禁/解封（纯标记策略）
- 管理员操作审计日志
- 独立管理后台前端区（`/admin`）与学生端两处小增量（申诉入口、举报弹窗）

**非目标（Out of Scope）**：

- 管理员**不得直接调整用户余额**；所有资金干预只能通过订单仲裁，且复用 Sprint 1 的
  `WalletService.freeze/unfreeze/settle`，不新增资金原语。
- 不做部分退款 / 按比例分账、多轮举证贴图、仲裁员分派、二审升级。
- 不做管理员分级（超级/普通），不做敏感词、系统公告。
- 不改变 S1/S2 已定的任何学生侧功能与页面。

## 4. 纠纷申诉与仲裁

### 4.1 订单状态机扩展

`OrderStatus` 枚举增加 `DISPUTED`（Sprint 1 Task 2 即预留该枚举值，但 S1 不实现入口，
全部行为在 Sprint 3 交付）：

```
PENDING ──接单/下单──▶ IN_PROGRESS ──交付──▶ CONFIRMING ──确认──▶ COMPLETED
   │                     │  ▲                  │  ▲
   │取消                 │  │                  │  │
   ▼                     └申诉┘                  └申诉┘
CANCELLED                  └──────▶ DISPUTED ◀──┘
                                         │ 申诉人撤回 → 回到 from_status
                                         │ 裁决 RELEASE_TO_SELLER → settle() → COMPLETED
                                         └ 裁决 REFUND_TO_BUYER  → unfreeze() → CANCELLED
```

规则：

- 仅 `IN_PROGRESS`、`CONFIRMING` 两态可发起申诉。
  - `PENDING` 不允许：悬赏无人接单，出资方自行「取消」即可解冻；服务单下单即 IN_PROGRESS。
  - 终态（COMPLETED/CANCELLED）不允许。
- 申诉成功后订单置 `DISPUTED`，原状态记入 `t_appeal.from_status`。
- `DISPUTED` 期间，accept / deliver / confirm / cancel 全部拒绝
  （返回「订单纠纷处理中，暂不能操作」）。
- 一个订单同时只允许一条 OPEN 申诉（服务层校验 + 唯一约束兜底，见 §12）。
- P2 的「超时自动确认」遇到 `DISPUTED` 必须**暂停计时、不得越过纠纷自动确认**。

### 4.2 发起与撤回

- 发起方：订单的 buyer 或 seller（悬赏里即发布者/接单者，服务里即下单者/帖主）。
- 必填：申诉理由（文字，≤500 字）。不做举证图片（非目标）。
- 撤回：仅申诉人本人，且申诉仍为 OPEN；订单恢复 `from_status`，申诉置 WITHDRAWN。
- 发起/撤回均通过 `NotificationService` 通知**对方**（类型 APPEAL_CREATED /
  APPEAL_WITHDRAWN）。后台申诉列表对新 OPEN 申诉可见（轮询，不做管理员实时通知）。

### 4.3 仲裁（仅 ADMIN）

后台申诉列表 OPEN 优先；仲裁人必须填写处理意见。两种裁决：

| 裁决 | 资金动作（复用 S1） | 订单终态 | 关帖规则 | 流水备注 |
|---|---|---|---|---|
| RELEASE_TO_SELLER（判收款方胜） | `settle(buyerId, sellerId, amount, orderId)` | COMPLETED | type=BOUNTY 才关帖（沿用 S2 Task 3） | 仲裁打款 |
| REFUND_TO_BUYER（判出资方胜） | `unfreeze(buyerId, amount, orderId)` | CANCELLED | type=BOUNTY 才关帖 | 仲裁退款 |

- 裁决后申诉置 RESOLVED，记录 outcome / admin_id / admin_comment / handled_at。
- 写 `t_admin_log`（action=APPEAL_RELEASE / APPEAL_REFUND，detail 含金额与意见）。
- 通知买卖**双方** APPEAL_RESOLVED（文案含裁决方向）。
- 整个仲裁方法 `@Transactional`，订单行用既有 `findByIdForUpdate` 悲观锁；
  必须先校验订单当前确为 DISPUTED 且该申诉 OPEN。

### 4.4 边界情形

- 申诉期间申诉人账号被封禁：申诉流程不中断（封禁为纯标记，见 §9），管理员仍可裁决。
- 服务帖（一帖多单）某一单进入纠纷：只影响该订单，服务帖保持 OPEN，其他人照常下单。

### 4.5 典型申诉场景（验收时的演示脚本）

设计背景：现有状态机里「取消」和「确认」都是**出资方单方掌握**的按钮，只保护出资方——
悬赏发布者/服务下单者可在进行中单方取消并即时退款；到待确认阶段则只能确认或干等
（P2 超时后还会自动打款给收款方）。申诉机制就是给这些单方按钮覆盖不到的争议提供出口。

**IN_PROGRESS（进行中）——以收款方申诉为主：**

- 悬赏：A 发布「帮取菜鸟驿站快递 ¥20」，B 接单后已到驿站取件，A 反悔点「取消」，
  钱即时退回、B 白跑。B 在 A 取消成功**之前**发起申诉，订单转 DISPUTED，取消被锁死，
  由管理员裁决劳务费归属。
- 服务：C 挂牌「高数一对一辅导 ¥60」，D 下单后 C 已按约上完课，D 以「没提分」为由
  要取消退款，C 发起申诉要求平台判付。
- 出资方少数场景：对方虚假接单、拖延不履行，希望平台介入留痕，而非自行默默取消。

**CONFIRMING（待确认）——双方对立最尖锐，出资方在这里获得唯一救济出口：**

- 出资方申诉（拒付）：B 标记已交付，但 A 发现快递没取到/拿错/物品损坏；
  或 D 发现 C 实际未授课、未交付资料。A 不能确认、也不能取消，只能申诉要求退款。
- 收款方申诉（催付）：B 已完好送达但 A 拖延不确认甚至失联；C 已上完课 D 恶意不确认。
  收款方申诉要求平台强制结算打款。

**其余阶段为何不可申诉：**

- PENDING：悬赏无人接单，无交易对手方（sellerId 为空），出资方自行取消即可；
  服务单不经过 PENDING（下单即 IN_PROGRESS）。
- COMPLETED / CANCELLED：资金归属已定，为避免裁决反复，终态不可翻案。

**关于「进行中单方取消」的明确规则（维持 S1 设计不变）：**

- 出资方在 IN_PROGRESS 仍可单方取消并即时退款，S3 **不改变**该规则；
- 但若该订单已存在 OPEN 申诉（已是 DISPUTED），取消接口按 §4.1 一律拒绝——
  即「先申诉者成功锁定订单」，不需要额外新增机制；
- 因此验收演示中，收款方申诉要在出资方取消成功之前发起；一旦订单已 CANCELLED，
  资金已退回、属终态，不再受理申诉（学生可改走举报通道反映对方恶意，由管理员按 §5 处置账号）。

## 5. 举报闭环

### 5.1 数据

`t_report` 由 Sprint 2 建表，Sprint 3 以 `ddl-auto=update` **只加列**：
`handler_id`、`handled_at`、`result`（VALID / REJECTED，可空）、`handle_comment`。
`status` 沿用 PENDING / HANDLED。

### 5.2 处理动作矩阵

管理员在举报详情调用统一接口 `POST /api/admin/reports/{id}/handle`：

| action | 执行 | result |
|---|---|---|
| DELETE_POST | 社区帖置 DELETED（复用 S2 逻辑） | VALID |
| CLOSE_TRADE_POST | 悬赏/服务帖置 CLOSED（复用 S2 逻辑） | VALID |
| BAN_USER | 被举报用户置 BANNED（纯标记，见 §9） | VALID |
| REJECT | 不做处置 | REJECTED |

- 接口内一次性完成：执行处置 → 回写 status=HANDLED、result、handler_id、
  handle_comment、handled_at → 写 `t_admin_log`（action=HANDLE_REPORT）→
  通知举报人 REPORT_HANDLED（文案含成立并已处置 / 驳回）。
- target_type 与 action 的匹配由后端校验（如对 POST 举报不能传 BAN_USER 之外的对象混淆；
  BAN_USER 作用于被举报内容的作者，若 target_type=USER 则作用于 target_id）。

### 5.3 防重复举报

同一 reporter 对同一 (target_type, target_id) 已存在 PENDING 举报时，拒绝再次提交
（服务层校验即可，课程范围不加数据库部分索引）。

## 6. 管理员订单视图

- **列表** `GET /api/admin/orders`：按订单状态、帖子类型（BOUNTY/SERVICE）、buyerId/sellerId、
  下单时间区间筛选；按 id 倒序。课程规模返回全量列表 + 前端 Element Plus 分页，不做后端分页。
- **详情** `GET /api/admin/orders/{id}` 聚合返回一条订单时间线：
  订单本体 → 关联 trade_post → buyer / seller 用户摘要（昵称、状态）→
  该订单关联的全部 `wallet_log`（order_id 命中）→ 关联申诉记录（t_appeal）。
- 管理员对订单**只读**；改变订单的唯一入口是申诉仲裁（§4.3），列表页对 DISPUTED 订单
  提供「去仲裁」跳转。

## 7. 资金托管监管

- 单用户视角：`GET /api/admin/users/{id}/wallet`（余额 + 冻结）、
  `GET /api/admin/users/{id}/wallet-logs`（全部流水倒序）。
- 全平台流水：`GET /api/admin/wallet-logs` 支持按 userId、流水类型、时间筛选。
- **冻结总额核对（答辩亮点）** `GET /api/admin/wallets/frozen-summary`：
  - 平台冻结总额 = `SUM(wallet.frozen)`
  - 在途订单应冻金额 = `SUM(trade_order.amount WHERE status IN
    (PENDING, IN_PROGRESS, CONFIRMING, DISPUTED))`
  - 返回两者与差额；正常应恒等（差额 0）。所有资金路径（发布冻结、取消解冻、
    正常结算、仲裁两条路径）都守恒，是本指标成立的前提。
- 不提供任何「后台充值 / 扣减 / 调账」接口（见 §2 非目标）。

## 9. 用户管理（封禁策略：纯标记）

- 封禁 = `user.status = BANNED`。登录时既有逻辑已拒绝（S1 UserService.login）。
- **不做任何联动**：在架悬赏/服务、社区帖、在途订单、钱包一律不动；
  管理员认为需要下架内容时，走举报处置或内容管理接口逐条手动处理。
- 提供解封 `POST /api/admin/users/{id}/unban`（置回 ACTIVE）。
- ban / unban 均写 `t_admin_log`。
- 备注：S2 Task 10 修改 JwtAuthFilter 时已查库取角色；S3 顺带让过滤器对 BANNED 用户
  的已签发 token 拒绝放行（一行判断），避免封禁后 token 有效期内仍可操作。

## 10. 管理员操作审计日志

- 新表 `t_admin_log`：admin_id、action、target_type、target_id、detail（≤500 字，
  存处理意见与金额等关键上下文）、created_at。
- 所有管理动作落表：BAN_USER / UNBAN_USER / DELETE_POST / CLOSE_TRADE_POST /
  HANDLE_REPORT / APPEAL_RELEASE / APPEAL_REFUND。
- 实现方式：`AuditLogService.record(...)` 由各管理服务**显式调用**（不用 AOP——
  课程项目里显式调用最直观、最好讲）。
- 查询 `GET /api/admin/logs`：按管理员、action、时间区间筛选，倒序。
- 日志只增不改不删。

## 11. 权限与管理端形态

- 后端：S2 Task 10 已把 ROLE_ADMIN 写入 SecurityContext；S3 在 `SecurityConfig` 统一配置
  `/api/admin/**` 要求 `hasRole('ADMIN')`，作为权限主防线；
  管理服务内保留 `requireAdmin` 作为业务层兜底。
- 学生举报接口 `POST /api/admin/reports`（S2 既有，学生调用）与管理接口同路径前缀，
  需在 S3 调整为学生侧路径 `POST /api/reports`，`/api/admin/reports` 仅管理员可读
  （S3 对 S2 接口的唯一微调，仅路径迁移）。
- 前端：独立 `AdminLayout`（侧边导航，不复用学生端顶栏），子路由
  `/admin/dashboard | orders | appeals | reports | users | wallets | logs`；
  路由守卫按 role 拦截。`LoginResp` 增加 `role` 字段并随登录态保存；
  学生端导航对 ADMIN 账号显示「管理后台」入口。
- admin 账号仍由 S2 的 AdminBootstrap 初始化（admin/admin123）。

## 16. 测试与验收要点

- **仲裁资金守恒**（仿 S1 WalletDomainTest）：
  - REFUND 后 buyer 余额复原、冻结归零，订单 CANCELLED；
  - RELEASE 后 seller 余额到账、buyer 冻结归零，订单 COMPLETED；
  - 两种裁决后 `frozen-summary` 差额仍为 0。
- **状态机挂起**：DISPUTED 订单调用 accept/deliver/confirm/cancel 全部抛 BizException。
- **权限**：学生账号访问任一 `/api/admin/**` 返回 403；学生只能对自己参与的订单申诉、
  只能撤回自己的申诉。
- **举报闭环**：四种 action 各走一遍；举报人收到结果通知；同人同对象重复举报被拒。
- **看板**：造数后各指标与库内 COUNT/SUM 手工核对一致；7 天序列日期连续。
- **审计**：每个管理动作后 t_admin_log 多一条且字段完整。
- 演示截图素材：纠纷全流程（申诉→挂起→两种裁决）、冻结总额核对、举报闭环、看板。

## 17. 已定决策（本篇）

1. 总工期延长至 11 周，管理保障以独立 Sprint 3（3 周）交付，S1/S2 不删功能、不加压。
2. 纠纷采用「DISPUTED 状态 + 申诉表 + 二选一裁决」标准仲裁流；不做多轮举证/部分退款/二审。
3. 仲裁资金动作完全复用 S1 的 `settle()` / `unfreeze()`，不新增资金原语，不开后台调账。
4. 举报为完整闭环（结果 + 处理人 + 意见 + 联动处置 + 通知 + 去重）。
5. 封禁为纯标记：只挡登录（顺带让 JWT 过滤器拦截 BANNED 的有效 token），
   不联动帖子/订单/钱包；提供解封。
6. 看板指标口径以本文 §8 为准；图表用 ECharts；数据看板由原 P2（PB-31）升为 P0。
7. 审计日志显式调用落表，不引入 AOP。
8. S1 Task 2 预留 `DISPUTED` 枚举值但不实现行为；S2 仅举报接口路径在 S3 迁移，其余不动。
