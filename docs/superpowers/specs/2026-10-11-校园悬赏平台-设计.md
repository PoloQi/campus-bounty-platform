# 校园悬赏平台 · 设计规格（Design Spec）

> 版本：v1.0 ｜ 日期：2026-10-11 ｜ 状态：待用户评审
> 说明：本规格由原「校园服务平台（技能服务 + 跑腿 + 社交）」改造而来，改版动因见第 1 节。

---

## 1. 背景与改版动因

原方案是三支柱结构：**技能服务（商家侧）+ 跑腿待办 + 社交搭子**。存在两个问题：

- **双端割裂**：技能服务依赖「商家入驻 + 管理员审核」，等于要维护两套用户端（学生端 + 商家端），与「一个校园平台」的定位不符。
- **业务不闭环**：交易无资金流转，跑腿「赏金」和技能服务「下单」都只是状态标记，缺少担保交易这条主线，答辩时讲不出「交易」的分量。

**改版方向**：把平台收敛为**单一学生用户端**的 **C2C 悬赏交易平台**（参照闲鱼），学生之间发布悬赏、挂牌服务、接单、担保交易，外加独立的社区交流模块。

---

## 2. 定位与角色

**一句话定位**：校园悬赏 —— 学生之间的互助悬赏交易平台（闲鱼式 C2C）+ 社区交流。
学生既能**发悬赏找人帮忙**，也能**挂牌服务接单赚钱**，还能发帖逛社区、找搭子。

| 角色 | 说明 | 客户端 |
|---|---|---|
| 学生用户 | 唯一登录角色：发悬赏 / 挂服务 / 接单 / 下单 / 交易 / 发帖 | 同一端 |
| 平台管理员 | 内容治理（删违规帖、下架悬赏）、用户治理（封禁） | 管理后台 |

> 「接单者」不是独立角色，而是学生用户的另一种身份——同一账号既能发悬赏也能接单。

---

## 3. 业务域总览

| 域 | 内容 | 来源 |
|---|---|---|
| ① 账户与钱包 | 注册登录、余额、充值(模拟)、冻结/可用、流水 | 改造自原「基础」 |
| ② 悬赏交易 | 需求悬赏 + 服务挂牌 → 订单 → 担保结算 | 合并原「跑腿」+「技能服务」 |
| ③ 社区 | 发帖、点赞、评论、找搭子、私信 | 保留原「社交搭子」 |
| ④ 治理 | 举报、删帖、封禁 | 精简管理员 |

---

## 4. 核心模型：统一悬赏交易模型（双模式）

设计要点：**需求悬赏与服务挂牌，本质是同一种交易的镜像**，用一套模型承载，避免为两种业务各写一套。

| 维度 | 需求悬赏 BOUNTY | 服务挂牌 SERVICE |
|---|---|---|
| 帖主身份 | 需求方（求人帮忙） | 供给方（提供技能） |
| 他人的动作 | 接单 | 下单 |
| 出资方（buyer） | 帖主 | 下单者 |
| 收款方（seller） | 接单者 | 帖主 |
| 一帖几单 | 1 帖 : 1 单（先到先得） | 1 帖 : N 单（可被多人购买） |

**建模方式**：
- 一张 `trade_post` 表，用 `type ∈ {BOUNTY, SERVICE}` 区分两种帖子；
- 一张 `order` 表，用 `buyer_id / seller_id` 表达资金方向——悬赏里 buyer = 帖主，服务里 buyer = 下单者；
- 两种模式**共用同一个订单状态机**，唯一差异是 `PENDING → IN_PROGRESS` 的触发动作（接单 vs 下单）。

> 答辩话术：我们没有为跑腿和技能服务各写一套，而是抽象出统一的悬赏交易模型，用 type 区分需求侧/供给侧，订单状态机复用。

## 5. 资金模型与订单状态机

### 5.1 钱包

- 每个用户一个钱包：`余额 balance` + `冻结 frozen` + `流水 wallet_log`。
- 充值走**模拟**（点一下 +100，或初始赠送 1000），不接真实支付。
- 所有资金变动**必须记流水**（充值 / 冻结 / 解冻 / 支出 / 收入）。

### 5.2 冻结时机（担保交易的关键）

- 发**悬赏** → **发布时即冻结**赏金（余额不足不允许发布，防止滥发；语义为「我的钱已押在平台上」）。
- 下**服务单** → **下单时冻结**货款。
- 统一表述：**出资方在发起交易动作时，资金即冻结进平台托管**。

### 5.3 订单状态机（两模式共用）

```
  ┌──────────┐   接单 / 下单    ┌──────────────┐   交付    ┌──────────────┐   确认    ┌───────────┐
  │ 待接单    │ ───────────────▶│ 进行中        │ ────────▶│ 待确认        │ ────────▶│ 已完成     │
  │ PENDING  │                 │ IN_PROGRESS  │          │ CONFIRMING   │          │ COMPLETED │
  └────┬─────┘                 └──────────────┘          └──────────────┘          └───────────┘
       │ 取消 / 超时
       ▼
  ┌───────────┐
  │ 已取消     │  解冻退回出资方
  │ CANCELLED │
  └───────────┘
```

- `PENDING → IN_PROGRESS`：悬赏靠**接单**触发，服务靠**下单**触发（唯一差异点）。
- `IN_PROGRESS → CONFIRMING`：接单者 / 服务者标记「已交付」。
- `CONFIRMING → COMPLETED`：出资方确认 → 解冻 + 打款给收款方（界面显示 1% 手续费，**不真扣**）。
- 旁支：无人接单可取消并解冻；超时未确认可自动确认（P2）。

## 6. 端到端业务流程

### 流程 A：悬赏闭环（求人帮忙）

```
A 充值获得余额
  → A 发布悬赏（标题/描述/赏金/截止/分类/图片）→ 系统冻结赏金 → 悬赏「待接单」
  → B 在「悬赏大厅」浏览 / 筛选 / 搜索 → B 接单 → 订单「进行中」
  → B 完成并标记交付 → 订单「待确认」
  → A 确认 → 解冻并打款给 B → 订单「已完成」→ 双方互评（可选）
旁支：A 在无人接单时可取消 → 解冻退回
```

### 流程 B：服务闭环（接单赚钱）

```
C 挂牌服务（我能提供摄影/代写/家教，价格 X）→ 服务「待下单」
  → D 在「服务市场」浏览 → 点进详情 → 下单 → 冻结 D 的货款 → 订单「进行中」
  → C 交付并标记 → 订单「待确认」
  → D 确认 → 打款给 C → 订单「已完成」
```

### 流程 C：社区闭环（交流 / 找搭子）

```
发帖（图文 + 标签）→ 信息流展示 → 点赞 / 评论
  → 找搭子：给帖子打「考研/运动/拼车」标签并按标签筛选
  → 可私信联系（WebSocket 一对一）
  → 管理员可删违规帖
```

### 横向能力

注册登录（JWT）· 个人中心（我的发布 / 我的接单 / 我的订单 / 我的帖子 / 我的钱包）· 站内通知（接单、交付、确认）· 搜索（交易为核心，**放开搜索**）· 管理员后台。

---

## 7. 社区与治理边界

- 社区与交易**松耦合**：帖子独立存在，不强制关联悬赏。「帖子一键转悬赏」列 P2。
- 找搭子**不单独建表**：即带分类标签的帖子 + 按标签筛选。
- 治理：`report` 举报表（可举报帖子/悬赏）+ 管理员删帖 / 下架悬赏 / 封禁用户。

---

## 8. 功能清单与优先级

### MVP（P0）

- 账户：注册 / 登录（JWT）、个人资料
- 钱包：余额展示、模拟充值、冻结/可用
- 悬赏：发布悬赏（冻结）、悬赏大厅（浏览/筛选/搜索）、接单、标记交付、确认
- 服务：挂牌服务、服务市场（浏览/筛选/搜索）、下单（冻结）、标记交付、确认
- 订单：订单状态流转、完成结算（解冻 + 打款）
- 个人中心：我的发布 / 我的接单 / 我的订单 / 我的帖子 / 我的钱包
- 社区：发帖（图文）、信息流、点赞、评论
- 治理：管理员删帖 / 下架 / 封禁

### P1

- 找搭子标签筛选 · 一对一私信（WebSocket）· 全局搜索 · 站内通知 · 双方互评（简单文字）· 钱包流水页

### P2

- 帖子转悬赏 · 超时自动确认 · 信用分 · 数据看板 · 收藏

### 非目标（Out of Scope）

真实支付 / 提现 · 商家入驻 · K8s / 云部署（本地 Docker 即可）· 群聊 · 已读回执 · 评分算法 · 第三方登录

## 9. 数据模型草案

| 表 | 关键字段 |
|---|---|
| `user` | id, 昵称, 头像, 简介, 联系方式, role(STUDENT/ADMIN), status(正常/封禁), 密码哈希 |

| `message` | id, from_id, to_id, content, created_at |

| `notification` | id, user_id, type, content, ref_id, is_read |

## 10. 新旧对照

| 旧 | 新 |
|---|---|
| 普通用户 + 商家 + 接单者 + 管理员 | **学生用户 + 管理员**（接单者是学生另一身份，不单列） |
| 技能服务：管理员录入 → 浏览 → 模拟下单 | **服务挂牌**：学生自己挂 → 浏览 → 下单（去商家、去管理员录入） |
| 跑腿：发布委托 → 接单 → 确认 | **需求悬赏**：发布 → 接单 → 确认（概念保留，升级为担保交易） |
| 无真实交易、无虚拟币 | **模拟余额 + 冻结托管 + 流水**（最大增量） |
| 社交搭子 | 社区（保留并成为独立域） |
| 商家入驻审核（PB-04 / PB-16a） | **删除** |

## 11. Sprint 切分建议（3 人 / 8 周）

- **Sprint 1（基础 + 交易内核）**：账户钱包 + 悬赏全闭环 + 订单状态机 + 冻结/结算。
  **先把「钱的闭环」跑通，这是全项目最硬的骨头。**
- **Sprint 2（服务 + 社区 + 治理 + 部署）**：服务挂牌下单、社区、找搭子、私信、搜索、通知、管理后台、Docker 打包。

---

## 12. 已定决策与遗留项

### 已定决策

1. 结算方式：**模拟余额托管**（余额 + 冻结 + 流水）。
2. 交易形态：**需求悬赏 + 服务挂牌双模式**，共用统一订单模型。
3. 社区定位：**独立信息流 + 找搭子标签**，与交易松耦合。
4. 管理角色：**保留精简管理员**（内容 + 用户治理，无商家审核）。
5. 手续费：界面显示 1%，**不真扣**（纯展示）。
6. 评价：**简单文字互评**，P1，不做评分算法。
7. 悬赏冻结时机：**发布即冻结**。
